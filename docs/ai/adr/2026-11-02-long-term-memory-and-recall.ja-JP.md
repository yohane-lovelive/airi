# 長期記憶: 意味による想起と端末間の同期

状態: 提案

## 背景

[ADR 2026-10-10](./2026-10-10-skills-automations-and-memory.md) は、キャラクターに長期記憶を与えました。各事実は、索引の行と本文を持つ 1 つのエントリーです。[ADR 2026-10-28](./2026-10-28-autonomous-character-perception-and-missions.ja-JP.md) は、その上に自律するキャラクターを作り、次の 4 か所でこの ADR を待っています。

- 後から接続した端末も、同じ記憶を持ちます。
- プロンプトは、想起した上位 5 件を持ち、索引全体は持ちません。
- 発話の型 `recall`、雑談の話題の種、話題の類似度は、意味で記憶を読みます。
- どの端末が話す権利を持つかを決める在席の記録は、サーバーが持ちます。

今のコードには、次の限界があります。

- エントリーは 1 台の端末の IndexedDB にあります。削除は墓標を残しますが、それを読む同期はありません。
- 各リクエストは、新しい順に 50 件の索引の行をシステムプロンプトに並べます。`builtIn_searchMemory` は、ほかのエントリーを文字の 2 文字組の一致で探します。同じ言葉は見つけますが、同じ意味は見つけません。
- クライアントには文章の埋め込みがありません。話題の類似度も 2 文字組を使います。
- 記憶を書くのは、`builtIn_writeMemory` を呼んだモデルだけです。会話の後で、その事実を拾う処理はありません。

バックエンドの構成は、すでに VectorChord 拡張つきの PostgreSQL を動かしています（`server/apps/api/sql/init.sql`）。キャラクターカードと設定は、すでに [server ADR 2026-10-06](../../../server/docs/ai/adr/2026-10-06-document-sync.md) のフィールドストアで同期しています。

## 決定

記憶の正本はサーバーです。埋め込みもサーバーが持ちます。端末は完全な写しを持つので、想起とチャットはサーバーなしでも動きます。

### 原則

- 1 つの想起の窓口が、すべての読み手に答えます。チャットの返事、`builtIn_searchMemory`、発話の型 `recall`、話題の種、話題の類似度です。
- 意味による想起にはサーバーが要ります。サーバーがないときは、同じ窓口が 2 文字組で想起します。これはサーバーを持たないオーナーのための、常に支える動き方で、旧方式ではありません。
- チャットのモデルは自由に替えられます。埋め込みのモデルはサーバーで固定なので、チャットのモデルを替えても、記憶とベクトルはすべて残ります。
- 記憶の文が端末から出るのは、オーナーがサインインしたサーバーへだけです。
- 想起した記憶は、リクエストのキャッシュされる先頭の部分を変えません。

### 埋め込みのモデル

- モデルは Google の EmbeddingGemma 2 で、ライセンスは Apache 2.0 です。100 を超える言語に対応し、日本語もその 1 つです。
- 文章の経路だけを動かします。文章の部分は約 2 億 7 千万パラメーターです。画像と音声のエンコーダーは読み込みません。
- ベクトルは 256 次元です。モデルは 768 次元を作り、Matryoshka の切り詰めに対応します。256 次元では、多言語の MTEB の値が 61.36 から 60.41 に下がり、保存の量は 3 分の 1 になります。
- クエリには `task: search result | query: ` を前に付けます。エントリーには `title: none | text: ` を付け、その後に索引の行と本文を続けます。
- サーバーは、Transformers.js と ONNX Runtime で動く小さな `embedder` サービスで、q8 の重みを使ってモデルを動かします。詳細は [server ADR](../../../server/docs/ai/adr/2026-11-02-memory-store-and-search.md) にあります。

### 記憶の同期

- 記憶はフィールドストアの機能 `/api/v1/memories` です。各エントリーが 1 つの文書で、その id はエントリーの UUIDv7 です。
- フィールドは `description`、`body`、`persona` です。全体の記憶には `persona` のフィールドがありません。
- 端末の墓標は、サーバーで文書の削除になります。サーバーの削除は、端末で墓標になります。
- 衝突には、フィールドストアの規則を使います。2 台が同じフィールドを変えたときはサーバーの値が残り、手元のエントリーは新しいエントリーになるので、事実は失われません。
- 同期は、設定の同期と同じく、レンダラーのリーダーが動かします。手元の変更の後、サインインのとき、ウィンドウが見えるようになったときです。
- クライアントの実験機能 `memory-sync` で有効にします。既定はオフです。

ステップ M2a は、同期を次のように作りました。

- `useMemorySyncStore()` が、リーダーで `libs/document-sync` の `synchronize` を動かします。どのウィンドウの変更も、メモリストアの `changeCount` として届き、続けて書いた後 1.5 秒で 1 回動きます。
- `updatedAt` は同期しません。編集のたびに変わるので、2 台が時刻だけで衝突するからです。初めて端末に届いたエントリーは、UUIDv7 の作成時刻を取るので、索引は事実の順番を保ちます。
- 他の端末からのフィールドは、サーバーと同じ上限を持つ Valibot のスキーマを通します。不正なフィールドのエントリーは、端末ではそのまま残ります。
- メモリストアは、`synchronize` の求めどおり、保存を待つ前に 1 回分のエントリーをすぐ書きます。その前に始まった読み込みは、それを置き換えません。
- 同期は、始める前にエントリーを読み直します。同期の間に別のウィンドウで編集したエントリーは、同じエントリーへのリモートの変更に負けることがまだあります。同期の間ずっとロックを持つと、ネットワークの応答を待つ間、記憶の書き込みがすべて止まるので、このまれな場合を受け入れます。

### 想起の窓口

`recallMemories({ query, personaId, limit })` は、クエリに一番合うエントリーを、良い順に返します。カード自身のエントリーと、全体のエントリーが対象です。

- 同期がオンでサーバーの準備ができていれば、`POST /api/v1/memories/search` を呼びます。サーバーはエントリーの id と点数を返します。クライアントは、手元の写しからエントリーを読みます。
- 最後の同期の後に端末で変わったエントリーは、まだサーバーにありません。クライアントは、それらも 2 文字組で点数を付け、サーバーの結果の後ろに置きます。
- サーバーのエラーのとき、または 1.5 秒たったときは、2 文字組で想起します。
- 窓口は、どの方法で答えたかを伝えます。インスペクターと IO トレースがそれを表示します。

### プロンプトの中の想起した記憶

ADR 2026-10-28 のプロンプト予算は、想起した記憶に上位 5 件、約 500 トークンを割り当てています。

- チャットの各リクエストの前に、クライアントは最新のオーナーのメッセージで 5 件を想起します。
- 想起したエントリーは、id、索引の行、本文とともに、タグ付きの部分として最新のユーザーのターンに入ります。履歴には保存しません。
- システムプロンプトは索引を持ち続けるので、モデルはどのエントリーも id で読めます。意味による想起が動くときは、索引は 50 件ではなく、新しい 20 件を並べます。
- 索引にあるエントリーも、想起した部分には本文とともに出ます。索引は 1 行しか示さないからです。
- IO トレースは、想起の方法、クエリの文字数、想起した id を記録します。

ステップ M2b は、想起を次のように作りました。

- `libs/memory-recall.ts` の `recallMemories` は、サーバーの結果と、最後の同期の後に変わった手元のエントリーを合わせます。`useMemoryRecallStore()` はサーバーを呼び、インスペクターのために最後の想起を記録します。記憶の文は記録しません。
- 同期を動かすのはリーダーだけなので、最後の同期の時刻を知るのもリーダーだけです。ほかのウィンドウの想起は、サーバーの結果だけを使います。
- チャットは、用途が `owner-reply` のターンで、LLM のスパンが始まる前に想起します。想起した部分は、リクエストの写しの中で、最新のユーザーのターンの runtime context に、ソース `memory:recall` として加わります。検索文は、ターンの時刻の接頭辞を除いたオーナーのメッセージです。
- 索引の件数は、サーバーの毎回の応答ではなく設定で決めます。記憶の同期が有効なら 20 件、そうでなければ 50 件です。応答ごとに件数が変わると、キャッシュされるシステムプロンプトが変わるからです。
- `builtIn_searchMemory` も同じ想起を使うので、その結果は想起した部分と同じになります。
- インスペクターは、最後の想起の方法、件数、クエリの文字数、時刻を表示します。
- 想起した部分がリクエストの写しに入り、保存される履歴には入らないことを、単体テストで確かめます。計画ではチャットストア全体のブラウザーテストとしていましたが、履歴に届きうるのはこの写しの手順だけです。

### 自律の読み手

- 発話の型 `recall` は、今の話題と場面でエントリーを想起します。コードは、そのうちの 1 件を状況ブロックに入れます。
- 雑談の話題の種は、新しいエントリーだけでなく、今の話題で想起したエントリーも使います。
- ステップ 2b-2a の話題の類似度は、話題のラベルをベクトルで比べます。`POST /api/v1/memories/embed` を呼びます。クライアントは最近のラベルのベクトルを持つので、1 つのラベルは 1 回だけ埋め込みます。
- サーバーがないときは、どの読み手も、今と同じく 2 文字組を使います。

ステップ M3 は、自律の読み手を次のように作りました。

- `libs/initiative/topic-vectors.ts` の `TopicVectors` は、ターンのラベルと種のうちベクトルのないものを 1 回のリクエストで埋め込み、約 500 件を持ちます。ポリシーは今も同期の関数で比べます。2 つのベクトルがそろわない組は、2 文字組で比べます。
- 短いラベルのコサインは高めに出ます。日本語の組での確認では、同じ話題が 0.80〜0.92、近い話題が 0.69〜0.86、ほかの話題が 0.64〜0.79 でした。`scaledCosine` は 0.70〜0.90 を 0〜1 に直すので、2 文字組の閾値がベクトルにも合います。話題の続きの閾値 0.5 は、コサイン 0.80 に当たります。ADR は、ベクトルと閾値の合わせ方を書いていなかったので、これは追加です。確認は 14 組でした。実際のターンのラベルで、範囲が動くことがあります。
- 埋め込みのルートは、クエリの前置きを使います。文の類似の前置きは、同じ話題とほかの話題を 0.79〜0.96 に集めたので、クエリの前置きのほうがよく分けました。
- 話題が温まっている間は、その話題に合う記憶 5 件を話題の種に加えます。冷えた話題は新しい話題を頼むので、加えません。
- `recall` のターンは、今の話題、なければ場面、なければ最後の行で想起します。最近 6 時間に出していない一番の記憶を、状況ブロックの 1 行で渡します。
- インスペクターは、話題をベクトルで比べたかどうかと、最後の `recall` のターンの記憶を表示します。

### 端末間で話す権利

- サーバーは、アカウントごとに 1 つの在席の記録を持ちます。端末の id、接続した時刻、最後のハートビートです。
- 最初に接続した端末が話す権利を持ちます。そのハートビートが 30 秒止まると、次の端末が引き継ぎます。
- 話す権利を持つ端末だけが、自律の発話とミッションを動かします。オーナーのメッセージへの返事は、オーナーが送った端末で再生します。
- ルートは [話す端末の server ADR 2026-11-02](../../../server/docs/ai/adr/2026-11-02-device-floor.md) にあります。

ステップ M4a は、話す権利を次のように作りました。

- PostgreSQL の 1 行が、アカウントごとの持ち主を持ちます。1 回の条件付き upsert が、最初の端末に権利を渡し、持ち主には持たせ続け、30 秒ハートビートがなければ次の端末に移します。
- 端末の id は、`localStorage` の乱数の UUID です。設定の同期の許可リストにないので、端末を出ません。
- `useDeviceFloorStore()` は、リーダーから 10 秒ごとにハートビートを送り、`pagehide` で権利を手放します。イニシアチブのランナーと watch のランナーは、権利を持つ端末だけで動きます。
- 同期ストアのランタイムは、ストアより先に `pagehide` で止まります。そのため、ストアはランタイムが最後に知らせたリーダーの状態を覚えておきます。
- 話す権利は、記憶の同期が有効な間だけ使います。サーバーの応答が 30 秒なければ、その端末が持ち主として動きます。ADR は、サーバーなしのときの端末の動きを書いていませんでした。オーナーは 1 度に 1 台を使うので、サーバーが落ちてもキャラクターが黙ってはいけません。
- リマインダーは、ステップ M4b が同期するまで、どの端末でも動いていました。
- インスペクターは、この端末が権利を持っているかを表示します。

### 記憶以外の記録

recipe、ミッション、意図、タイムラインのメモは、ステップ M4 まで端末に残ります。その後、ミッションと意図は記憶と同じく同期します。それらを動かすのは、話す権利を持つ端末だけです。タイムラインのメモは 1 つの画面のことなので、端末に残ります。

ステップ M4b は、同期を次のように作りました。ルートは [server ADR 2026-11-03](../../../server/docs/ai/adr/2026-11-03-autonomy-records.md) にあります。

- 同期するのは、リマインダーと意図だけで、`/api/v1/autonomy-records` を使います。雑談、実況、watch は、その端末の画面とその時に結びつくので、端末に残ります。ADR はミッションと書いていたので、これは範囲を狭めます。
- 文書は `kind` と `record` を持ちます。サーバーは種類と大きさだけを確かめます。クライアントは各記録を Valibot のスキーマで確かめ、文書の id と合わない記録は断ります。
- 衝突で負けた手元の分は捨てます。リマインダーの写しは、オーナーに 2 回知らせてしまいます。動いているリマインダーを変えるのは話す権利を持つ端末だけなので、衝突は設定画面で 2 か所が同時に編集したときにしか起きません。
- ミッションのランナーは、話す権利を持つ端末でだけリマインダーを届けます。記憶の同期が、この同期と話す権利を一緒にオンにするので、2 台が 1 つのリマインダーを届けることはありません。
- `useLeaderDocumentSync` が、記憶とこれらの記録の同期のループをリーダーで動かすので、2 つのストアは 1 つのループを共有します。

### オーナーのプロフィールと記憶の作業

ステップ M5 は、使用量の用途 `memory` を持つ 2 つの裏の作業を加えます。

- 約 300 トークンのオーナーのプロフィールの要約。ADR 2026-10-28 のプロンプト予算が、その枠を取っています。
- 終わった会話を読み、モデルが保存しなかった事実を書き、同じことを言うエントリーをまとめる作業。

ステップ M5a は、記憶の作業とプロフィールを次のように作りました。同じことを言うエントリーをまとめるステップ M5b は、この後に書きます。

- 会話は、20 分静かになると終わったとみなします。作業は、オーナーの開いている会話の前回の作業より後の部分を、最大 60 件、20,000 字まで読みます。通知はオーナーの言葉ではなく文脈として扱い、オーナーの言葉がない部分は飛ばします。
- 作業は、カードのチャットモデルに、会話の書き起こしと、オーナーの言葉に一番近い記憶 8 件を渡します。モデルは `report_memories` ツールで答えます。最大 5 件で、それぞれ新しい記憶か、関連する記憶の id を付けた更新なので、写しを足しません。答えた時点で呼び出しを止めます。
- エントリーは `memory.write` を通るので、同期と記憶のツールの規則が効きます。
- 作業を動かすのは、話す権利を持つ端末のリーダーだけです。失敗した作業は 30 分待つので、壊れたプロバイダーにかかる費用は小さくなります。
- 事実を保存した作業の後、モデルはカードの記憶と全体の記憶から、オーナーのプロフィールを最大 1,200 字で書き直します。設定画面はそれを表示し、オーナーは編集、消去、今すぐ書くことができます。
- プロフィールは、autonomy records の種類 `profile` の 1 件の記録なので、どの端末も同じものを送ります。ADR は、プロフィールの置き場所を書いていませんでした。
- オーナー自身の会話のシステムプロンプトがプロフィールを持ちます。変わるのは作業の後だけなので、キャッシュされる先頭はめったに変わりません。
- 記憶の作業とプロフィールは、どちらも長期記憶の設定で、既定はオフです。その呼び出しは、使用量の用途 `memory` として数えます。

ステップ M5b は、まとめる作業を次のように作りました。

- 記憶の作業の各処理の後、まとめる作業は、前回のまとめから変わったカードのエントリーを、古い順に最大 10 件調べます。ADR は、どのエントリーを読むかを決めていませんでした。
- 調べる各エントリーについて、まとめはカードの近いエントリーを 4 件見つけます。記憶の同期が動いている間は意味による想起で、それ以外は共通の文字で全体を調べます。0 から 1 の 1 つの尺度で比べ、0.35 以上の組が候補になります。
- 単位は組です。1 回のまとめは、最も似た組を 5 つ送り、1 つのエントリーを 2 つの組に入れません。待つ組のエントリーは未確認のまま残るので、後のまとめがその組を見つけます。同じ事実の 3 つの写しは、2 回のまとめでまとまります。
- 対象は、カード自身のエントリーだけです。共通のエントリーはオーナーのもので、実行は忘れられません。ADR は、まとめる対象を限っていませんでした。
- カードのチャットモデルは `merge_memories` ツールで答えます。組ごとに、まとめた 1 つのエントリーか、別々の事実を示す null です。まとめは新しいほうのエントリーに書き、もう一方を記憶のストアで忘れるので、同期がそれを運びます。組の外の ID を含む答えは拒否します。
- 端末は、モデルが別々の事実と判断した組を覚え、もう一度は尋ねません。
- 設定画面は、前回の処理でまとめた重複の数と、最近のまとめの前後の説明を表示します。まとめは元に戻せないので、オーナーが何が変わったかを確かめられます。
- まとめが失敗しても、処理で保存した事実は残り、次の処理が同じエントリーを調べ直します。
- 2026-11-04 のこの端末には記憶がなかったので、実機確認では日本語の 18 件のテスト記憶と `deepseek-v4.1-flash` を使いました。同じ事実の言い換えが 6 組、近いが別の事実が 3 組です。共通の文字は、写しで 0.37〜0.64、近い事実で 0.38〜0.77、別の事実で 0〜0.2 だったので、0.35 のしきい値は別の事実だけを落とします。
- 確認で 2 つの不具合が見つかり、このステップで両方を直しました。グループが「オーナーは」のような語で無関係なエントリーをつなぎ、1 つの答えが本物の写しを別々にしたので、単位を組にしました。また、次のまとめの開始位置が、1 回で送れなかったグループを飛ばしていました。修正の後、約 7 秒のまとめ 2 回で、6 組の写しをすべてまとめ、近い 3 組は別々に残しました。

## ほかの ADR との関係

- ADR 2026-10-10 は、索引がすべてのエントリーを並べると書いています。ADR 2026-10-28 のステップ 2-4 が、すでに 50 件に絞りました。この ADR は、意味による想起が動くときに 20 件に絞ります。
- ADR 2026-10-28 は、「Memory and devices」でこの ADR への依存を挙げています。この ADR は、そこにある予定の方向を置き換えます。
- server ADR 2026-10-31 は、記憶、recipe、ミッションを設定の同期から外しました。この ADR がそれらを引き受けます。

## 目標外

- 端末での埋め込み。スマートフォンの Web アプリはモデルをうまく動かせず、すべての端末が同じベクトルを計算することになります。
- プロバイダーの埋め込み API。オーナーは自分のサーバーでのモデルを選びました。
- 画像、音声、画面の埋め込み。EmbeddingGemma 2 は対応していますが、この ADR は文章だけを埋め込みます。
- アカウントの間で共有する記憶。
- フレームの同期。フレームは、話すモデルへ送るとき以外、端末を出ません。

## 既知のリスク

| リスク | 対応 |
| --- | --- |
| カタログの Transformers.js（3.8.1）が EmbeddingGemma 2 を読み込めない。対応は 4.3.1 からです。 | ステップ M1 で分かりました。オーナーは、embedder だけで 4.3.2 を使うことを選びました。1 つのパッケージを 2 つのカタログに置くと lint が通らないので、embedder の `package.json` が版を固定します。アプリは 3.8.1 のままです。 |
| 遅いサーバーが、チャットの返事をすべて遅らせる。 | 想起はリクエストのほかの準備と並べて動かし、1.5 秒であきらめます。 |
| 同期なしの端末で書いた記憶が、サーバーに届かない。 | 最初の同期で、手元のエントリーをすべて送ります。 |

## 検証

- サーバーのルートのテスト: 送信、一覧、削除、オーナーとペルソナで絞った検索、埋め込みのルート、embedder が止まっているときの応答。
- embedder のテスト: 前に付ける文、256 次元への切り詰め、正規化。実際のモデルの確認は手で行います。CI はモデルをダウンロードしないからです。
- クライアントの単体テスト: エントリーのフィールドへの対応、サーバーの結果と手元の変更の合わせ方、時間とエラーでの切り替え、プロンプトの部分。
- クライアントのブラウザーテスト: 想起した部分が最新のユーザーのターンに届き、履歴には届かないこと。
- オーナーの日本語の記憶を使った手での想起の確認: エントリーと言葉を共有しない質問、たとえばラーメンのエントリーに対する「好きな食べ物は？」。
- 2026-11-03 の実機確認では、Docker のスタック、デスクトップ版、2 つの Web のオリジンで、ステップ M1 から M5a を試しました。不具合が 4 つ見つかり、その後の変更で直しました。
  - embedder のイメージのユーザーにホームがなく、corepack が起動時に失敗しました。
  - 報告のツールで止めた呼び出しが、トークンを記録しませんでした。
  - `pagehide` での権利の手放しが、動いていませんでした。
  - 想起の検索文に、ターンの時刻の接頭辞が入っていました。

## 残る作業

- 実際のデータで、記憶の機能の上限を決めます。文書の数、バイト数、履歴です。
- 索引がシステムプロンプトを出られる時期を決めます。
- オーナーの PC で、想起の遅れを測ります。ステップ M1 の確認では、モデルの読み込みに約 10 秒、CPU で 1 件のクエリに約 130 ms かかりました。
