# 自律動作: 見て話す 1 つのモデル、プロバイダーの中継、判定用モデル

Status: accepted

英語版: [2026-11-14-autonomy-one-model-relay-decision.md](2026-11-14-autonomy-one-model-relay-decision.md)

## 背景

`docs/ai/adr/2026-10-28-autonomous-character-perception-and-missions.ja-JP.md` が、画面の認識、ミッション、実況の設計を定めている。オーナーは、モデルのサーバーに OpenCode Go を使ってこの設計を動かした。その中で 3 つの問題が出た。

### 実況が遅い

オーナーは 2026-11-13 に、1 つのゲームの録画した試合で実況を測った。

- 遅さの原因はモデルだった。`mimo-v2.6-pro` は最初のトークンまで 5〜45 秒かかった。`gpt-6-luna` は画像 1 枚で約 1.3 秒だった。
- 画面用に 2 つ目のモデルを置いても良くならなかった。画像を読むモデルと会話のモデルを分けると、間違った行は 76 行中 29 行から 13 行に減った。ただし 1 行ごとに 3〜5 秒遅くなった。
- オーナーは、すべてのターンを 1 つのモデルにすると決めた。`gpt-6-luna` が画面を見て話す。

### ブラウザから OpenCode Go を呼べない

以下は、2026-11-13 と 2026-11-14 に `https://opencode.ai/zen/go/v1` へ送ったリクエストで確かめた内容である。

- どのリクエストにも `x-opencode-session` ヘッダーが要る。ないと、サーバーは HTTP 400 `MissingSessionID` を返す。
- サーバーは、`/chat/completions` への CORS の事前確認に HTTP 404 を返す。`/models` が許可するヘッダーに `x-opencode-session` はない。
- 推論を切るフィールドはモデルごとに違う。違うフィールドを送ると HTTP 400 になる。サーバーのモデル一覧からは、どのフィールドかが分からない。

オーナーは、各アプリの Vite の設定に `server.proxy` を書いてサーバーを呼んでいた。この設定は AIRI の部品ではない。デスクトップ版の設定はコミットされておらず、「OpenAI 互換」のプロバイダーを手作業でそこに向けていた。

### 話すタイミングには判定が要る

タイマーで実況すると、何も起きていないときに話し、出来事を逃す。オーナーは 2026-11-13 と 2026-11-14 に、この判定に使う判定用モデルを試した。

- Gemini Decision 1（`gemini-decision-1`）は、画面の 2 フレームについての「はい / いいえ」の質問に答える。ゲームの名前を使わない質問 1 つで、重要な出来事 56 件の 98% を拾い、反応は 1 分に 6.3 回だった。画像の解像度を low にして、1 回の呼び出しは 0.85 秒、入力は 748 トークンだった。
- 文字だけから 4 つの答え（オーナーに答える、画面に反応する、自分から話題を出す、黙る）を選ばせると、101 場面中 88 場面で正しかった。1 回の呼び出しは 0.35 秒、入力は 361 トークンだった。
- 場面とその正解は、検証を書いた者が作った。ゲームは 1 タイトルの 1 試合だけである。

## 決定

### 返事と実況を 1 つのモデルにする

- ターンは、セッションのキャラクターの会話モデルを使う。返事、実況の行、その他の自律的なターンのすべてに当てはまる。
- 認識の設定にあった、画面専用のモデルをなくす。`gpt-6-luna` は画像を読めるので、2 つ目のモデルは画面を読まない。
- モデルを決める場所は、今までどおりモジュールの設定である。規則は `docs/ai/adr/2026-11-11-module-defaults-and-character-values.md` にある。

### OpenCode Go のプロバイダー定義

`packages/stage-ui/src/libs/providers/providers/opencode-go` が、プロバイダー `opencode-go` を定義する。

- 設定が持つのは API キーだけである。ベース URL は持たない。中継の URL はアプリごとに違い、設定はアプリの間で同期されうるからである。
- 推論のフィールドはモデルに従う。定義の中の表が、実測した 9 つのモデルの形を持つ。表にないモデルには、推論のフィールドを送らない。
- モデル一覧はサーバーから取る。どのモデルが画像を読めるかが分かるので、オーナーがモデルごとに設定しなくてよい。
- モバイル版には中継がないので、このプロバイダーを出さない。

### プロバイダーの中継

`packages/stage-shared/src/provider-relay` の `createProviderRelay` が、ページのリクエストをモデルのサーバーへ転送する。

- 宛先の一覧は固定である。入っているのは `opencode-go` だけである。他の宛先へのリクエストには HTTP 404 を返すので、中継は誰でも使えるプロキシにならない。
- 中継がセッションのヘッダーを付ける。セッションの値は、中継を動かすホストの起動ごとに 1 つ作る。
- 中継は API キーを持たない。ページが自分の `Authorization` ヘッダーを送り、中継はそれを転送する。
- 転送するのは `authorization`、`content-type`、`accept` である。ページのクッキーとオリジンは上流へ送らない。
- 応答はストリームのまま通す。

中継を動かすホストは、アプリごとに 1 つである。

| アプリ | ホスト | アドレス |
| --- | --- | --- |
| デスクトップ版 | Electron の main（`protocol.handle`） | `airi-relay://opencode-go/` |
| Web 版 | Vite の開発サーバーとプレビューサーバー | ページのオリジンの `/provider-relay/opencode-go/` |

- デスクトップ版の経路は、Electron 43 の隠しウィンドウで確かめた。`http` のオリジンのページが、`Authorization` ヘッダー付きの JSON を独自スキームへ POST し、応答を分割して受け取れた。
- 2 つの Vite の設定から `server.proxy` を削る。
- Web 版のビルドを静的に配置した場合、中継はない。後から API サーバーに経路を足せば対応できる。

### 会話モデルの横に判定用モデルを置く

- Gemini Decision 1 は、話すタイミングを判定する。画面の説明はせず、台詞も書かない。
- ページは Gemini API を直接呼ぶ。サーバーは、`x-goog-api-key` への CORS の事前確認に応答する。
- API キーは、プロバイダー `google-generative-ai` のキーを使う。新しい設定項目は作らない。
- クライアントは `packages/core-agent` に置く。画面の判定と 4 択は、後の変更でこの上に足す。

## 採らなかった案

- **会話モデルの前に画像を読むモデルを置く。** 間違った行は減ったが、1 行ごとに 3〜5 秒遅くなった。
- **汎用の CORS プロキシ。** どの URL にも転送する中継は、ページがアプリを通してすべてのホストに届くようにしてしまう。
- **Electron の main にローカルの HTTP サーバーを立てる。** ポートが要り、そのポートを伝える呼び出しがウィンドウごとに要る。独自スキームにはどちらも要らない。
- **デスクトップ版も API サーバーの経路を使う。** ローカルのバックエンドが動いていないと、会話が止まる。
- **中継の URL をプロバイダーの設定に入れる。** デスクトップ版の設定が同期されると、Web 版が動かなくなる。
- **話すタイミングを画素の検出で決める。** 同じ頻度の反応で、拾えた重要な出来事は 73% だった。

## 手順

| 手順 | 内容 | ワークスペース | 状態 |
| --- | --- | --- | --- |
| 1 | プロバイダーの中継、その 2 つのホスト、プロバイダー `opencode-go`。 | `packages/stage-shared`、`packages/stage-ui`、`apps/stage-tamagotchi`、`apps/stage-web`、`packages/i18n` | この変更 |
| 2 | Vite のプロキシの設定と、認識の設定の画面用モデルを削る。 | `apps/stage-web`、`packages/stage-ui`、`packages/stage-pages`、`packages/i18n` | 未着手 |
| 3 | Gemini Decision 1 のクライアント。 | `packages/core-agent`、`packages/stage-ui` | 未着手 |
| 4 | 画面の判定、4 択、実況の行に渡すフレーム。 | `packages/core-agent`、`packages/stage-ui` | 未着手。この文書に専用の節を足す |

## 影響

- 「OpenAI 互換」と Vite のプロキシを使っていたオーナーは、プロバイダー「OpenCode Go」を足して、そのモデルを選び直す必要がある。古い設定を移すコードはない。
- オーナーが選んでいた画面用モデルは、手順 2 の後は使われない。画面のターンは、キャラクターの会話モデルを使う。
- Web 版が OpenCode Go に届くのは、`pnpm dev:web` またはプレビューサーバーで動かしたときだけである。
- OpenCode Go がモデルを足したら、推論の表を更新する必要がある。それまで、新しいモデルはサーバーの既定どおりに推論する。
- 手順 4 の後、自律的なターンには Gemini の API キーが要る。無料枠は 1 日 10,000 リクエストである。

## 手順 1 の確認

- 単体テストが、中継、Node 用のアダプター（実際の HTTP サーバーを使う）、独自スキームのハンドラー、プロバイダー定義を確かめる。
- 2026-11-14 に、Web 版の開発サーバーの中継を通して確かめた。モデル一覧は 30 件、キーなしの会話リクエストはサーバーの HTTP 401、`gpt-6-luna` のストリーム応答は最初の文字まで 1.0 秒だった。
- デスクトップ版の中継は、アプリの中でサーバーに対しては動かしていない。その確認には、アプリの設定にオーナーのキーが要る。
