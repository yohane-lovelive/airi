# Unity の部屋を歩く

Status: accepted

英語版: [2026-11-10-unity-stage-room-walking.md](2026-11-10-unity-stage-room-walking.md)

## 背景

Unity ステージは、キャラクターを部屋の中に表示できる。この試作は [Unity ステージの ADR](2026-11-06-unity-stage-sidecar.ja-JP.md) の「部屋の状態」に書いてある。キャラクターは 1 つの立ち位置に立ち、そこから動かない。

オーナーは、キャラクターが部屋の中で暮らしているようにしたい。

- 誰も話しかけていないときは、部屋の中を歩き、ところどころで少し立ち止まる。
- オーナーが話しかけたときは、立ち止まり、オーナーのほうを向いて話す。
- 後のステップでは、ゲーム実況のときに部屋のモニターの前へ行く。このステップはこの ADR の範囲外である。

コードの次の事実が、設計の制約になる。

- `CharacterDriver` は、1 つの待機クリップとジェスチャーを混ぜる。待機はホストが `.vrma` ファイルで送る。リポジトリに歩行のクリップはない。
- クリップは、最初のフレームからの腰の移動を `StagePose.HipsX`、`HipsY`、`HipsZ` で渡す。
- `Stage.vue` は、AIRI が考え中か（`presenceBubble.thinking`）、話し中か（`nowSpeaking`）を知っている。Unity ステージは、どちらの状態も受け取らない。
- Unity プロジェクトには AI モジュールがないので、NavMesh がない。
- VRChat のワールドでは、壁と床には当たり判定がある。家具にはないことが多い。部屋の取り込みは、立ち位置の探索の間だけ、家具に仮の当たり判定を付ける。
- UniVRM v0.131.4 には `VrmAnimationExporter` がある。このクラスは、フレームごとのボーンの回転から `.vrma` ファイルを書く。

## 決定

この ADR はステップ W1 を追加する。部屋の中の歩行、オーナーのほうを向く動き、ついて行くカメラである。ステージのほかの試作と同じく、各部分はプレイヤーの引数か環境変数で有効にするまでは無効のままである。

### 歩ける範囲

部屋の取り込みは、Unity のパッケージである AI Navigation 2.0（`com.unity.ai.navigation`）で NavMesh を焼く。

- 取り込みは、部屋のシーンの新しいオブジェクトに `NavMeshSurface` を付ける。この Surface は描画用のメッシュを集めるので、家具も焼く対象になる。
- 焼くときのエージェントは、半径 0.25 m、高さ 1.7 m である。そのため、テーブルや低い棚の下は NavMesh に入らない。
- 取り込みは、`NavMeshData` をシーンの隣にアセットとして保存する。シーンのバンドルがこのデータを持ち、部屋のシーンを読み込むと Surface が NavMesh に足す。
- `StageRoom` のコードは `NavMeshSurface` 型を使う。そのため、プレイヤーのどのシーンにも Surface がなくても、プレイヤーのビルドはこの型を残す。

### 開けるドア

ワールドのドアは閉じたメッシュなので、閉じたドアはその部屋を NavMesh から切り離す。2LDK では、閉じたドアが洗面所、2 つの部屋、バルコニーを切り離していた。オーナーは、バルコニーも含めて開けることを選んだ。

- 取り込みは名前でドアを探す。`door`、`ドア`、`扉`、`戸` を含み、`frame` と `枠` を含まないものである。触れ合うドアは 1 つの組にする。たとえば引き戸の板である。
- 取り込みは組ごとに、その組を隠して焼き、立ち位置から行ける床を測る。行ける床が 1.5 m² 以上増えたときだけ、その組を隠したままにする。そのため、収納、開いているドア、玄関のドアはそのままになる。
- 新しい部屋の奥に、さらにドアがあることがある。そこで探索は最大 3 回くり返す。
- `room.json` の `openDoors` に、開けたドアを並べる。前の一覧は次の取り込みでも残るので、オーナーは一度書き換えればよい。
- 隠したドアは回ったり滑ったりしない。戸口は空になる。焼いた光と反射には、閉じたドアが残る。

最初の判定は、ドアの両側を見ていた。一方の側に行ける床があり、もう一方の側に立ち位置から行けない床があるかである。引き戸の板と、部屋の裏にある収納で、この判定は誤った。そこで取り込みは、組ごとに増える床を測る。

| 案 | 中身 | 結果 |
| --- | --- | --- |
| **AI Navigation 2.0** | `NavMeshSurface` が Editor で焼く。Unity のパッケージがデータを持ち、読み込み時に足す。 | 採用。Unity の通常の方法で、Editor で歩ける範囲を目で確かめられる。 |
| AI モジュールだけ | `NavMeshBuilder` が Editor で焼く。AIRI の部品がデータを持つ。 | パッケージは増えないが、AIRI のコードが増え、Editor で歩ける範囲を見られない。 |
| AIRI の格子 | 立ち位置の探索の格子で経路を探す。 | Unity の AI を使わないが、経路が角ばり、なめらかにする処理が AIRI のコードになる。 |

### 歩行のクリップ

歩行は、Quaternius の Universal Animation Library（CC0）から取る。

- オーナーがパックをダウンロードする。AIRI の Editor ツールが、その歩行のクリップをヒューマノイドで再生し、`VrmAnimationExporter` で `walk.vrma` を書く。
- このツールは `pnpm run import:motion` で動く。`.cache/motions/<name>/` の FBX ファイルのクリップ `Walk_Loop` を、`Assets/StreamingAssets/AiriMotions/walk.vrma` に変換する。
- CC0 はリポジトリへのコピーを許す。そこで `walk.vrma` を Unity プロジェクトに入れ、プレイヤーが持つ。この ADR に入手元を書く。
- 歩くのは Unity ステージだけである。そこでクリップは Unity プロジェクトに置き、プロトコルにはこのクリップのメッセージを足さない。
- クリップはその場で再生する。ドライバーは歩行のクリップの `HipsX` と `HipsZ` を捨て、上下の揺れのために `HipsY` を残す。

| 案 | ライセンス | Git | 結果 |
| --- | --- | --- | --- |
| **Quaternius の Universal Animation Library** | CC0 | 入れられる | 採用。無料版にはパックの約 60〜70% が入っている。歩行が入っているかは、オーナーが確かめる。 |
| BOOTH の歩行モーション | 再配布禁止 | 入れられない。ローカルのコピーだけ | オーナーの購入になる。 |
| Mixamo | 単体ファイルの再配布禁止 | 入れられない。ローカルのコピーだけ | Adobe のアカウントが要る。 |
| AIRI の手続き的な歩行 | 制限なし | 入れられる | ファイルは要らないが、見た目が一番不自然になる。 |

### 移動

`Core` の新しいクラス `WanderPlan` が、キャラクターの行き先を決める。Unity を参照しないので、`dotnet` でテストできる。

- `WanderPlan` には 3 つの状態がある。休む（Rest）、歩く（Walk）、注目する（Attend）である。
- 休む時間は 6〜20 秒の乱数である。その後、計画が新しい行き先を選ぶ。
- 行き先は、立ち位置と同じ床の上の NavMesh の点で、2 m 以上離れた点である。さらに各端から 0.5 m 以上離れているので、壁に顔を向けて止まらない。
- 歩くのは、行き先に着くか、制限時間を過ぎるまでである。歩き終わると、一番開けた方向を向く。
- 注目は、ホストが見ている人への注目を求めたときに始まる。ホストが解除すると終わり、また休む状態に戻る。

Stage 側は `NavMeshAgent` でキャラクターを動かす。

- アバターは、`StageRoot` の子の新しい Transform の下で動く。エージェントはこの Transform を動かす。
- エージェントは彼女の向きを変えない。Stage 側が、体を経路の次の角へ毎秒 240 度で向ける。
- 速さは体の向きに従う。そのため歩き始めには先に向きを変え、横へ滑らない。
- 速さは 0.8 m/s である。待機のクリップに対する歩行のクリップの重みは、エージェントの速さに従う。
- 歩行のクリップは、エージェントの速さに合わせて速く、または遅く再生する。そのため、足の滑りが少なくなる。
- `--airi-wander` または `AIRI_UNITY_STAGE_WANDER=1` で有効になる。部屋がないときは、この引数は何もしない。

### 見ている人への注目

プロトコルにホストのメッセージ `host.character.attention` を 1 つ足す。ペイロードは `{ "target": "viewer" }` か `{ "target": "none" }` である。

- Electron は、対象が変わったときに送る。サイドカーの状態が新しく `running` になったときも、待機と同じく送り直す。
- AIRI が考え中か話し中の間と、その後の 15 秒は、対象は `viewer` である。その後は `none` になる。
- `viewer` のとき、キャラクターは立ち止まり、約 0.5 秒で体をウィンドウのカメラに向ける。頭と目は、首の範囲の中でカメラを見る。
- フレームの手続き的なオフセットは、この向きの上に重ねる。そのため、呼吸とうなずきは続く。

W1-3 は次のように作る。

- レンダラーでは、`stage-ui` の `useStageSidecarAttention` が対象を決める。デスクトップアプリのブリッジは最後の対象を覚え、新しく `running` になったときに `viewer` を送り直す。
- `Core` の `GazeAim` は、首と頭を左右に 50 度まで、上下に 25 度まで向ける。この回転の 40% を首が受け持つ。
- 残りの角度は目が受け持つ。左右に 12 度まで、上下に 8 度までである。向きは 0.3 秒で入り、0.3 秒で抜ける。
- 体は毎秒 360 度で回るので、半回転は 0.5 秒である。頭が先にカメラへ向く。
- サイドカーがこのメッセージに従うのは、W1 のほかの部分と同じく `--airi-wander` のときだけである。この引数がなければ、ステージの見た目は今までと同じである。
- アプリで 2LDK のときにチャットを送ると、AIRI が考えている間、彼女はカメラの方を向いた。返事の後に注目が終わり、また歩き出した。

| 案 | 中身 | 結果 |
| --- | --- | --- |
| **新しいホストのメッセージ** | Electron が注目を決め、Unity は動かすだけである。 | 採用。Unity ステージの ADR のとおり、Electron が頭脳のままになる。メッセージはまれで、1 秒に 30 回ではない。 |
| フレームに 2 つの項目 | 各フレームに `speaking` と `thinking` を入れ、Unity が決める。 | 頭脳の判断を Unity が持つことになる。 |
| Unity での推測 | Unity が口の重みを読む。 | プロトコルは変わらないが、考え中が分からず、話の途中の沈黙を話の終わりと取り違える。 |

Unity ステージの ADR は、見ている人への視線をステップ U5 に置いている。W1 はその一部、ウィンドウのカメラへの視線を先に入れる。ディスプレイの前の人への視線は、引き続きステップ U5 で足す。

### カメラ

ウィンドウのカメラはキャラクターについて行く。

- カメラの注視点は、毎フレーム、なめらかにアバターの中心について行く。
- 歩いている間、横回転と縦回転はワールドに対して固定のままである。そのため、彼女が向きを変えるたびに画面が回ることはない。
- 注視点からカメラへの球の当たり判定（SphereCast）で、最初の壁を見つける。カメラは壁の手前で止まるので、カメラとキャラクターの間に壁が入らない。
- 部屋の箱は、外側の制限として残る。
- キー 1、2、3、マウス、`--airi-camera` は、今までどおり働く。

W1-2 はこの一部を先に入れる。注視点は彼女について行くが、なめらかにはしない。これがないと、彼女が画面の外へ歩いて出るからである。なめらかさと球の当たり判定は W1-4 で足す。

W1-4 は残りを次のように作る。

- `Core` の `StageCameraFollow` は、注視点を 0.25 秒の時定数でなめらかにする。壁はカメラをすぐに寄せ、カメラは 0.5 秒で戻る。
- 球の半径は 0.15 m である。ワールドの壁は 1 枚の面のことがあるので、当たり判定は面の裏にも当たる。MMD モデルのコライダーは壁ではない。
- 壁は、カメラを注視点から 0.3 m より近くへは寄せない。
- ワールドはドアにコライダーを付けないことが多い。そこで部屋を読み込むとき、表示中の各ドアに、描画物の境界から箱を付ける。
- この決まりは、`--airi-wander` がなくても、どの部屋でも働く。マウスでもカメラを壁の向こうへ回せるからである。部屋がなければ、カメラは今までどおりである。

撮影では、壁ぎわに立つ彼女の腰と手だけが映った。壁の手前には、全身が入る場所がないからである。そこで W1-4 は、カメラを彼女のまわりにも動かす。これは上の「横回転は固定」を変える。

- カメラは、構図の距離の 60% 未満になると、20 度きざみで 120 度までの回転を試す。
- 距離の 90% 以上が取れる回転が続く範囲の、真ん中を選ぶ。幅のある範囲が勝ち、次にカメラに近い範囲が勝つ。
- 45 度までの回転は、毎秒 90 度までで回る。それより大きい回転は、2 台のカメラの間のように切り替える。廊下で回ると、途中で壁を向くからである。
- オーナーの角度にまた 1 秒続けて場所があれば、カメラはそこへ戻る。

W1-4 の最後の撮影では、2 体の VRM サンプルが 2LDK を 70 秒ずつ歩いた。カメラと彼女の間に壁が入ったコマはなかった。家具にはコライダーがないので、ソファや机が彼女の手前に入ることはある。

| 案 | 中身 | 結果 |
| --- | --- | --- |
| **追従カメラ** | カメラは角度を保ち、注視点が彼女について行く。壁がカメラを近づけるか、彼女のまわりへ動かす。 | 採用。部屋のデータなしで、どの部屋でも働く。 |
| 固定カメラ | 今のカメラ。 | 彼女が画面の外へ歩いて出る。 |
| 演出 | 部屋の視点を切り替える。 | 見栄えは良いが、部屋ごとに視点が要る。後のステップで足せる。 |

## ステップ

各ステップは、オーナーがその計画を承認してから始める。

| ステップ | 内容 | 完了の条件 |
| --- | --- | --- |
| W1-0 | この ADR | オーナーが受け入れる。 |
| W1-1 | 部屋の取り込みでの NavMesh と、プレイヤーでの読み込み | 2LDK で、立ち位置から乱数の 20 地点のうち 18 地点以上へ経路が引ける。 |
| W1-2 | `walk.vrma`、ドライバーの歩行の層、テスト付きの `WanderPlan`、エージェント、彼女について行くカメラの注視点 | 60 秒間の撮影で、新しい場所へ歩き、家具や壁に入らない。 |
| W1-3 | プロトコル、Electron、Unity の `host.character.attention`。両側のテスト付き | テストのメッセージでカメラのほうを向き、アプリでのチャットでも同じになる。 |
| W1-4 | 追従カメラのなめらかさ、球の当たり判定、壁のまわりへの動き。計算は `Core` でテストする | 撮影で、カメラとキャラクターの間に壁が入らない。 |

## この設計がしないこと

- 意味のある場所はない。たとえばモニター、ソファ、ベッドである。座ることもない。後の ADR で、`room.json` の場所と一緒に足す。
- 部屋のモニターでのゲーム実況はしない。
- three.js のステージでは歩かない。
- 階段は使わない。行き先は立ち位置と同じ床の上にとどめる。
- 開け閉めするドアはない。取り込みは、床を切り離すドアを一度だけ開け、ドアは開いたままになる。
- 動く物はよけない。部屋の中でほかに動く物はないからである。
- 家具はカメラを止めない。カメラを止めるのは、壁、床、ドアだけである。
- マイクからの注目はない。W1 は考え中と話し中の状態だけを読む。

## リスク

| リスク | 結果 | 対応 |
| --- | --- | --- |
| Quaternius のパックの無料版に歩行のクリップがない。 | W1-2 にクリップがない。 | オーナーが先にダウンロードを確かめる。表のほかの入手先は選択肢として残る。 |
| 足が滑る、または足の運びがおかしい。 | 歩行が不自然に見える。 | クリップの速さをエージェントの速さに合わせる。W1-2 での VRM サンプルの撮影では、接地した靴が歩く速さの約 8% だけ滑った。PMX モデルでも確かめる。その後、歩幅を 1.30 / 0.90 の 92% にした。足の骨のログでは、接地した足の動きは歩く速さの 2% 以内になった。 |
| プレイヤーのビルドが `NavMeshSurface` を外す。 | NavMesh が読み込まれない。 | `StageRoom` がこの型を使う。W1-1 でプレイヤーのログを確かめる。 |
| ワールドを焼くと NavMesh に切れ目ができる。 | 行けない行き先がある。 | 計画は行ける点だけを選ぶ。W1-1 でその割合を測る。 |
| 狭い廊下でカメラが揺れる。 | 画面が落ち着かない。 | カメラをなめらかに動かし、撮影で確かめる。W1-4 では廊下で切り替えが起き、撮影で揺れは見えなかった。 |
| PMX モデルの歩き方が VRM モデルと違う。 | PMX モデルの脚がおかしくなる。 | リポジトリに PMX モデルはない。オーナーのモデルで確かめる。W1-4 の後、オーナーの PMX モデル 2 体が、正しい脚で 2LDK を歩いた。カメラの方を向き、髪とスカートは落ち着いていた。画像での足の滑りの測り方はこの 2 体には使えず、目で見る限り足は滑っていなかった。 |
