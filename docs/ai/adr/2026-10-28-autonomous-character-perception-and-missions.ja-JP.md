# 自律するキャラクター: 知覚、発話の圧力、ミッション

ステータス: proposed

英語版: [2026-10-28-autonomous-character-perception-and-missions.md](./2026-10-28-autonomous-character-perception-and-missions.md)

> この文書は英語版 ADR の日本語訳です。内容が食い違う場合は英語版が正です。

## 背景

AIRI が話すのは、オーナーのメッセージかモジュールのイベントを受けたときだけです。オーナーは、Neuro-sama のように、自分で振る舞うキャラクターを求めています。
オーナーの要件は 4 つあります。

1. キャラクターが、オーナーのメッセージなしに会話を始める。
2. キャラクターが、PC の画面を知覚しながら話す。
3. キャラクターが、オーナーに任されたタスクをこなす。例は、ゲーム実況とリマインドです。
4. VRM モデルが、待機ループだけでなく、生成された自然なモーションで動く。

オーナーは、TTS 発話とのリップシンク要件を一旦取り下げました。コードには `useVRMLipSync` がありますが、未検証のまま据え置きます。

### 以前の試行で分かったこと

オーナーは最初の設計を試し、3 つの問題を見つけました。以下の原因は仮説です。リプレイ評価で検証します。

- **キャラクターが、画面について話し続ける。** 画面の説明が、毎回のプロンプトに「最新の状態」として入っています。モデルは、プロンプトの中で最も目立つ事実に反応します。
- **2 段の LLM では、反応が固定される。** 1 段目の LLM は、オーナーのメッセージだけから、短い振る舞いのラベルを選びます。時間に沿った状態がないため、ラベルは少数の値に収束します。
- **実況が浅い。** 視覚モデルが、各画像をテキストに変換します。チャットモデルはテキストだけを読むため、動きと経緯が失われます。

### 現在のコード

- `packages/stage-ui/src/stores/chat.ts` の `notifyConversation` は、オーナーのメッセージなしにターンを開始できます。モデルは話すか、黙ります。黙った通知は履歴に残りません。
- 画面のパイプラインは、`devtools/vision.vue`、視覚モデル、テキストのコンテキストの順です。カタログが画像入力を宣言しているチャットモデルは、画像を直接読みます(`use-chat-vision.ts`)。
- キャラクターのノートブックには、`dueAt` を持つタスクがあります。オーケストレーターは、期限が来た各タスクに `spark:notify` を送ります。モデルがタスクを作るツールはありません。
- VRM のアニメーションは `idle_loop.vrma` の 1 本と、表情の切り替えだけです。ローダーと `AnimationMixer` は既にあります。

## 決定

AIRI に、知覚の層、発話判断の層、ミッションの層、モーションの層を追加します。脳(要件 1〜3)と身体(要件 4)は、独立して出荷できます。
すべての機能は既定でオフで、`apps/stage-tamagotchi` のみが対象です。

### 原則

- 沈黙が既定です。出来事か内的な欲求が閾値を超えたときに、キャラクターは話します。
- 発話するモデルは、ピクセルを見ます。発話するモデルのために、画像をテキストに変換する段はありません。
- 過去はテキストが運びます。画像は履歴に残さず、短いメモのタイムラインを残します。
- 多様性はコードが持ちます。状態と乱数が多様性を作ります。2 段目の LLM は作りません。
- オーナーの指示は、明示的なミッションになります。ミッションの時刻と終了は、コードが保証します。
- キャプチャはローカルで無料です。モデルに送る画像だけにコストがかかるため、予算で上限を設けます。
- ツールは特定のゲームを知りません。ジャンル固有のロジックはコードに含めません。

### 発話モデル

- 発話モデルは、画像入力を受け取りテキストを返すチャットモデルです。
- Gemini Live のように音声で直接応答するリアルタイムモデルは対象外です。
- モデルはオーナーが後から選びます。設計は特定のプロバイダーに依存しません。
- 視覚モジュールは、画像入力のないチャットモデル向けの代替として残します。その場合、実況の品質は下がります。

### 知覚

- キャプチャは PC 上で動き、コストはかかりません。リングバッファが、直近 60 秒のフレームを最大 2 fps で保持します。メモリ上だけに置きます。
- 検出器は、モデルを呼ばずにコードで動きます。画面の変化、動きの量、大きな音、アプリの切り替え、長い静止を報告します。
- どの検出器も特定のゲームを知りません。各検出器のイベントには、顕著度の値があります。
- バッファはプロンプトに含めません。フレームがモデルに届くのは、判断ターンのときだけです。

### 画像予算

- オーナーは、1 時間あたりの画像枚数で予算を設定します。既定は低くします。
- 予算は、モデルに送るすべての画像を数えます。
- 予算が少なくなると、コードは判断ターンの間隔を延ばします。予算が尽きると、次の時間まで画像は送られません。
- 設定画面に、現在の 1 時間で送った画像枚数を表示します。

### 発話の圧力

- イベントは、顕著度に応じて圧力を加えます。圧力は時間とともに減衰します。長い沈黙は、退屈の項を加えます。
- 各モードには、基本の閾値があります。毎回のチェックで、閾値にランダムなゆらぎを加えるため、ターンの間隔はばらつきます。
- 各ターンの後には、不応期があります。黙ると決めたときは、圧力の一部だけを下げます。
- ゲートは、オーナーが入力中または発話中のとき、音声の再生中、ターンの実行中に、ターンを止めます。オーナーの入力が常に優先です。
- 判断から再生までの間に、顕著なイベントが起きたら、コードは古くなった発話を捨てます。
- オーナーは、基本間隔、静音時間、1 日の予算を設定します。既定は控えめです。

### 判断ターン

- 圧力が閾値を超えたら、コードが発話モデルを呼びます。
- リクエストには、新しいフレーム、タイムライン、最後の発話からの経過時間、内的状態のヒントを含めます。
- フレームは、等間隔ではなく、前回のターン以降に最も変化したフレームを選びます。最新のフレームは元のサイズにし、古いフレームは縮小します。
- 各フレームは 1 度だけモデルに送ります。古いフレームが示していた内容は、タイムラインが運びます。これにより、1 ターンのコストを新しいフレームの分だけに抑えます。
- イベントの後には、リクエストにイベント直前のフレームを含められます。遅れたリアクションでも、原因を見て話せます。
- 画像は、このリクエストだけに含まれます。履歴には、発話のテキストとタイムラインのメモが残ります。
- モデルは、話すか、黙るか、`noteTimeline` ツールでタイムラインにメモを書きます。

### タイムライン

- タイムラインは、時刻付きの短いメモのリストです。
- コードは、アプリの切り替え、オーナーの発話、ミッションの開始を書き込みます。モデルは、見たことを書き込みます。例は「ボス戦が始まった」です。
- 古いメモは要約して、リストを短く保ちます。
- タイムラインは、画面で起きたことの唯一の履歴です。

### リアルタイム性の高いゲーム

- モデルの呼び出しと音声の再生には、数秒かかります。オーナーはこの遅れを許容します。
- そのため、実況には 2 つのスタイルがあります。イベントの後には、キャラクターはイベント直前のフレームを見て事後リアクションをします。合間には、定期的な実況をします。
- 古くなった発話を捨てるルールにより、新しいイベントの後に遅れたセリフが再生されるのを防ぎます。
- オーナーは、ミッションの自由記述でゲームを説明します。コードはゲームのプロファイルを持ちません。

### 内的状態と多様性

- 内的状態は、エネルギー、気分、退屈、好奇心、直近の発話の記録です。コードが、時間とイベントから更新します。
- 発話の型は、反応する、茶化す、質問する、記憶を思い出す、独り言を言う、静かに観察する、のどれかです。コードが重みを付けて型を抽選します。
- 最近使った型は、重みが下がります。
- コードは、抽選した型を、同じ呼び出しの中で軽いヒントとして渡します。決まった割合のターンでは、ヒントを渡しません。
- リクエストには、キャラクターの直近の発話を含めるため、モデルは同じ書き出しと構造を避けます。
- この設計は、2 段目の LLM を追加しません。

### ミッション

オーナーの指示は、ミッションになります。モデルがツールで作成します。オーナーは設定ですべてのミッションを見て、それぞれを停止できます。

| 種類 | 例 | 動作 |
| --- | --- | --- |
| `reminder` | 「18時に薬の時間だと教えて」 | コードが時計を確認します。キャラクターは必ず話します。アプリが閉じていた場合は、次の起動で見逃したリマインドを伝えます。 |
| `commentary` | 「このゲームを実況して」 | 知覚が敏感になり、発話の予算が増えます。対象のウィンドウが閉じるか、オーナーが止めると、ミッションは終了します。 |
| `watch` | 「ダウンロードが終わったら教えて」 | ミッションは、検出器に条件を登録し、条件が成り立つと通知します。 |

- 通知に `mustSpeak` オプションを追加します。現在の通知は、モデルが可視の返答を返さないと黙るため、リマインドを運べません。
- ミッションは、デバイスに保存します。レンダラーのリーダーが時計を確認します。

### 身体: モーション

オーナーは、外部の人型 VRM モデルを使います。ボーンや表情はモデルごとに異なります。

- 読み込み時に、コードはモデルが持つヒューマノイドボーンと表情を調べます。
- 足りない部位を必要とするクリップやマーカーはスキップします。足りない機能はエラーを出さずにオフになります。
- `.vrma` クリップは正規化されたヒューマノイドボーンを使うため、1 つのクリップが多くのモデルに適合します。

3 つの層を重ねます。次の順に作ります。

1. **ライブラリ。** モデルが `<|MOTION:name|>` マーカーを書くと、`.vrma` クリップのセットが再生されます。クリップは、手を振る、うなずく、肩をすくめる、笑う、などの身振りを含みます。
2. **発話連動の手続き生成。** 音声の振幅が、頭のうなずきと上半身の揺れを動かします。
3. **生成モーション。** ツールがテキストから `.vrma` クリップを作り、ライブラリが結果をキャッシュします。

- モーションは、`AnimationMixer` の上半身の層で、0.2〜0.4 秒のクロスフェードで再生します。待機ループは続きます。
- 表情は別の層です。
- 生成は、発話ごとの処理ではありません。数秒から数分かかります。ライブラリに一致がないリクエストは、最も近いクリップを再生し、後で使うために生成をキューに入れます。
- オーナーはどのモーション素材元も許容します。コミュニティのツール Text-To-VRMA があります。この ADR は、そのライセンスと品質を検証していません。最初は、ライブラリを作るために、オフラインで使います。

### プライバシー

発話モデルはクラウドモデルです。フレームが PC の外に出るため、初回リリースから次のルールを必須にします。

- 画面の知覚はオプトインです。設定画面に、アプリが選択したクラウドプロバイダーにフレームを送ることを明記します。
- 知覚の動作中は、インジケーターを表示します。1 クリックで一時停止できます。
- 除外リストに、アプリとウィンドウタイトルを指定します。一致したフレームはスキップします。既定のリストには、パスワードマネージャー、銀行、メッセンジャーを含めます。
- 知覚は、サスペンド時、ロック画面時、ソースが消えたときに一時停止します。
- アプリは、フレームをディスクに保存しません。

## 実装の境界

- `packages/core-agent` が、移植可能なポリシー(圧力、閾値、ゲート、予算、発話の型、ミッションのルール、タイムライン)を持ちます。これらは、時計と乱数源を入力に取る純粋関数です。
- `packages/stage-shared` が、フレームの比較と検出器を持ちます。Vue への依存はありません。
- `packages/stage-ui` が、ストア、リングバッファ、判断ターン、ミッションのストア、ツールを持ちます。
- `packages/stage-ui-three` が、モーションの層とマーカーの再生を持ちます。
- `apps/stage-tamagotchi/src/main` が、アイドル時間とウィンドウ一覧を持ちます。Eventa コントラクトは `apps/stage-tamagotchi/src/shared` に置きます。
- 文字列は `packages/i18n` に置きます。変更するのは、英語ロケールと作成者のロケールだけです。
- レンダラーのリーダーが、知覚、圧力、ミッションを実行します。他のウィンドウは状態を読むだけです。

## ADR 2026-10-10 との関係

[ADR 2026-10-10](./2026-10-10-skills-automations-and-memory.md) は、自動実行レシピを定義しています。`main` のコードには、automation も `armRecipe` ツールもありません。
`reminder` ミッションは、その ADR の `modelTimed` の実行に対応します。`commentary` ミッションには対応するものがありません。声を持つ前景モードだからです。
`trigger`、`condition`、`cooldown` などの名前は、その ADR に合わせます。ミッションに関わる各ステップの前に、upstream の作業を確認します。

## 検証

意見だけでは、振る舞いを判定できません。リプレイ評価は、同じ入力で方式を比較します。

- ステップ 0〜2 は、偽の時計を使った合成イベントストリームを使います。ステップ 3 で、時刻付きのフレームと音声を保存するレコーダーと、録画から知覚と判断を実行するリプレイを追加します。
- 指標は、1 分あたりのターン数、沈黙の割合、書き出しと構造の重複(`distinct-n`)、発話の型のエントロピー、1 時間あたりの送信画像枚数です。
- 判定モデルが、発話がその窓の中の実際のイベントに触れているかを確認します。別のチェックが、タイムラインとの矛盾を見つけます。
- 評価は、`evals/asr-rewrite` と `evals/tts-speech-formula` の形式に従います。
- 偽の時計と固定の乱数源を使った決定的テストで、圧力、ゲート、予算、発話の型、ミッションを検証します。
- 実際のクラウドモデルと実際の画面を使ったライブ確認は、CI の対象外です。結果は PR に記録します。

## 非ゴール

- リップシンクの作業。オーナーが一旦取り下げました。
- 音声と映像のリアルタイム・ストリーミング API。最初の設計は、判断ターンを使います。
- ローカルの視覚モデル。初回リリースが対応するのは、クラウドプロバイダーのみです。
- `stage-web` と `apps/stage-tamagotchi-kirie` での画面の知覚。
- 画面の内容に基づく PC の操作。コンピューター操作は、専用のツールが担当します。
- フレームの保存と、長期の画面履歴の保存。
- ゲーム固有の検出器やプロファイル。

## ステップ

順序は依存関係に従います。各ステップは、前のステップの部品を使います。

| ステップ | 内容 | 状態 |
| --- | --- | --- |
| 0 | 画面なしのポリシーコア: `core-agent` の圧力、ゲート、内的状態、発話の型。合成イベントによる評価ハーネス。 | 未着手 |
| 1 | ミッション基盤と `reminder`: `mustSpeak` の通知、保存、ミッション一覧、ツール。 | 未着手 |
| 2 | 画面なしの自律発話: ポリシーコアを、沈黙とタイマーのトリガーで `notifyConversation` に接続する。多様性を計測する。 | 未着手 |
| 3 | 知覚: ローカルキャプチャ、リングバッファ、検出器、画像予算、レコーダー、画像付きの判断ターン、タイムライン、`commentary` と `watch` ミッション。 | 未着手 |
| 4 | モーション: モデルの対応ボーン・表情の確認、ライブラリ、マーカー、上半身の層、発話連動の手続き生成。 | 未着手 |
| 5 | 生成モーション、記憶からの話題、仕上げ。 | 未着手 |

ステップ 4 は、ステップ 0〜3 に依存しません。発話出力の形式変更を 1 度で済ませるため、ステップ 0〜3 の後に置いています。

## 未解決の作業

- 画像入力に対応した発話モデルを選び、既定の画像予算を決める。
- ステップ 1 の前に、upstream の Issue と PR で automation の作業を確認する。
- 既定の除外リストを、オーナーと決める。
- リアルタイム API を、後の ADR で扱うかを決める。
