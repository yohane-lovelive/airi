# 自律するキャラクター: 知覚、発話の圧力、ミッション

ステータス: proposed

英語版: [2026-10-28-autonomous-character-perception-and-missions.md](./2026-10-28-autonomous-character-perception-and-missions.md)

> この文書は英語版 ADR の日本語訳です。内容が食い違う場合は英語版が正です。

## 背景

AIRI が話すのは、オーナーのメッセージかモジュールのイベントを受けたときだけです。オーナーは、Neuro-sama のように、自分で振る舞うキャラクターを求めています。
オーナーの要件は 4 つあります。

1. キャラクターが、オーナーのメッセージなしに会話を始める。
2. キャラクターが、PC の画面を知覚しながら話す。
3. キャラクターが、オーナーに任されたミッションをこなす。例は、リマインド、ゲーム実況、見張り、雑談です。
4. VRM モデルが、待機ループだけでなく、自然なモーションで動く。

オーナーは、どの端末でも同じキャラクターと話すことを求めています。PC では、デスクトップ版と web 版が同じように動きます。スマホでは、web 版が画面の知覚なしで動きます。
オーナーは、TTS 発話とのリップシンク要件を一旦取り下げました。コードには `useVRMLipSync` がありますが、未検証のまま据え置きます。

### 以前の試行で分かったこと

オーナーは最初の設計を試し、5 つの問題を見つけました。以下の原因は仮説です。リプレイ評価で検証します。

- **キャラクターが、画面について話し続ける。** 画面の説明が、毎回のプロンプトに「最新の状態」として入っています。モデルは、プロンプトの中で最も目立つ事実に反応します。
- **振る舞いがカオスになる。** ミッションごとに専用のシステムプロンプトを追加し、何をするかをモデルがプロンプト全体から決めていました。プロンプトに情報が多すぎました。
- **2 段の LLM では、反応が固定される。** 1 段目の LLM は、オーナーのメッセージだけから、短い振る舞いのラベルを選びます。時間に沿った状態がないため、ラベルは少数の値に収束します。
- **実況が浅い。** 視覚モデルが、各画像をテキストに変換します。チャットモデルはテキストだけを読むため、動きと経緯が失われます。
- **雑談が 1 つの話題に留まる。** 別の LLM 呼び出しが話題を作り、コードが選んだ 1 つの話題を毎ターン渡していました。モデルはその話題に留まり、関連する話題へ移りませんでした。

### 現在のコード

- `packages/stage-ui/src/stores/chat.ts` の `notifyConversation` は、オーナーのメッセージなしにターンを開始できます。モデルは話すか、黙ります。黙った通知は履歴に残りますが、返答は残りません。
- 画面のパイプラインは、`devtools/vision.vue`、視覚モデル、テキストのコンテキストの順です。カタログが画像入力を宣言しているチャットモデルは、画像を直接読みます(`use-chat-vision.ts`)。
- キャラクターのノートブックは、`dueAt` を持つタスクをメモリ上だけに持ちます。オーケストレーターは、期限が来た各タスクに `spark:notify` を送ります。モデルがタスクを作るツールはありません。
- レシピと長期記憶は IndexedDB にあり、1 件ごとに 1 レコードです。端末の中に留まります。チャットとキャラクターカードは、サーバーと同期します。
- 各実行は、記憶の索引の全件をプロンプトに入れます。記憶が保存されるのは、モデルが `builtIn_writeMemory` を呼んだときだけです。`compactConversationEntries` はありますが、呼び出し元がありません。
- `stage-web` は、デスクトップ版と同じ synced Pinia のランタイムで、レンダラーのリーダーを選びます。
- VRM のアニメーションは、`idle_loop.vrma` の 1 本、表情の切り替え、まばたき、目の動きです。ローダーと `AnimationMixer` は既にあります。

## 決定

AIRI に、知覚の層、発話判断の層、ミッションの層、モーションの層を追加します。脳(要件 1〜3)と身体(要件 4)は、独立して出荷できます。
すべての機能は既定でオフです。対象は `apps/stage-tamagotchi` と `apps/stage-web` です。

### 原則

- 沈黙が既定です。出来事か内的な欲求が閾値を超えたときに、キャラクターは話します。
- 状態とリズムはコードが持ちます。言葉はモデルが持ちます。モデルは、ツールで、状態の小さな決められた範囲に書き込めます。
- プロンプトの各部分には、大きさの上限があります。モデルは、必要なときにツールで追加の情報を読みます。
- 発話するモデルは、ピクセルを見ます。発話するモデルのために、画像をテキストに変換する段はありません。
- 過去はテキストが運びます。画像は履歴に残さず、短いメモのタイムラインを残します。
- 多様性はコードが持ちます。状態と乱数が多様性を作ります。2 段目の LLM は作りません。
- オーナーの指示は、ミッションになります。ミッションの時刻と終了は、コードが保証します。
- キャプチャはローカルで無料です。モデルに送る画像だけにコストがかかるため、予算で上限を設けます。
- コードは特定のゲームを知りません。ジャンル固有のロジックはコードに含めません。
- どの端末でも同じ脳が動きます。どの機能が動くかは、端末の能力で決まります。

### 端末

| 端末 | 脳、ミッション、モーション | 画面の知覚 |
| --- | --- | --- |
| デスクトップ版 | あり | あり。確認なしでキャプチャを始められます。ウィンドウ一覧とシステムのアイドル時間が分かります。 |
| PC の web 版 | あり | 制限付きであり。下を参照。 |
| スマホの web 版 | あり | なし。ブラウザが画面をキャプチャできないことをコードが検出し、知覚をオフにします。 |

2 つのアダプターが、違いを隠します。画面のソースと、在席のソースです。在席のソースは、アイドル時間とウィンドウ一覧を報告します。
web 版には、次の制限があります。

- `getDisplayMedia` は、ページを読み込むたびに、共有の選択をオーナーに求めます。タブを閉じると、キャプチャは止まります。
- ブラウザは、ウィンドウ一覧もアプリ名も教えません。画面全体の共有では、アプリの切り替えの検出と除外リストが働きません。
- Chromium 系のブラウザでは、Idle Detection API が、許可の確認の後でアイドル時間を返します。
- 裏にあるタブは、タイマーが遅くなります。これを避けるため、タイマーは Worker で動かします。
- 閉じたタブは話せません。次にページを読み込んだときに、見逃したリマインドを伝えます。

`apps/stage-pocket` と `apps/stage-tamagotchi-kirie` は、この ADR の対象外です。

オーナーは、普段は 1 つの端末だけを使います。2 つの端末が開いているときは、1 つの端末が発言権を持ちます。

- 先に接続した端末が、接続を切るまで発言権を持ちます。その後、次の端末が発言権を受け取ります。
- 自律発話とミッションを実行するのは、発言権を持つ端末だけです。
- オーナーのメッセージへの返答は、オーナーが送った端末で再生します。
- 発言権にはサーバー上の在席の記録が必要なため、記憶の ADR がこれを定義します。それまでは、オーナーは 1 度に 1 つの端末だけを開きます。

### 発話モデル

- 発話モデルは、画像入力を受け取りテキストを返すチャットモデルです。
- 既定は、OpenCode Go の `deepseek-v4.1-flash` です。2026-10-30 の時点で、公開のモデル一覧は画像入力とツール呼び出しを宣言していました。
- 推論は遅延を増やすため、実況では推論の強さを `low` にします。
- オーナーは、いつでもモデルを変えられます。記憶はテキストなので、モデルを変えてもすべての記憶が残ります。
- 画像入力のないモデルでは、視覚モジュールを代替として使います。その場合、実況の品質は下がります。
- ツール呼び出しのないモデルは、ミッションの作成、タイムラインのメモ、見張りの確認への回答ができません。
- CORS のため、web 版には OpenCode Go 用のプロキシが必要です。dev サーバーにはあります。本番のビルドには、別の解決策が必要です。
- Gemini Live のように音声で直接応答するリアルタイムモデルは対象外です。

### 状態の持ち主

状態はコードが持ちます。モデルは、その一瞬の言葉を決めます。

| 決めること | 持ち主 |
| --- | --- |
| いつ話すか、長く黙り続けるか | コード: 圧力、ゲート、不応期 |
| どのミッションが動いているか、いつ始まり、いつ終わるか | コード: ミッションの状態 |
| モード。例は、普段か実況か | コード |
| 割り込むか、古くなった発話を捨てるか | コード |
| 画像の枚数と 1 日のターン数 | コード: 予算 |
| 発話の型の候補 | コード: 重み付きの抽選 |
| 何を言うか、このターンは黙るか | モデル |
| 画面で何を見たか | モデル: ツールで書くタイムラインのメモ |
| 見張りの条件が成り立ったか | モデル: ツールで返す「はい」か「いいえ」 |
| 後で何をしたいか | モデル: ツールで書く意図。上限あり |
| 一定の間、どれだけ話すか | オーナー: チャットの言葉。ツールが設定に変換します |

- 意図は短いメモです。例は「後でオーナーに旅行のことを聞く」です。コードは数を制限し、それぞれに期限を付けます。
- コードは、意図を圧力と話題の種に変えます。モデルは、気分も小さな決められた幅で動かせます。
- この状態を書き込むのは、レンダラーのリーダーだけです。他のウィンドウは読むだけです。

### オーナーによる調整

オーナーは、言葉で話す量を変えられます。例は「30 分静かにして」や「もっと話していいよ」です。

- ツールが、依頼を設定の変更に変換します。コードは各値を検証し、決められた範囲に収めます。
- 変更は、一時的なものか恒久的なものです。一時的な変更には、終了時刻があります。例は、静かにする期間です。
- このツールを使えるのは、オーナーのメッセージに答えるターンだけです。
- 暗黙のフィードバックも、話す量を変えます。オーナーが自律発話に反応しないと、間隔が少しずつ延びます。オーナーが反応すると、元に戻ります。
- インスペクターと設定画面が、今の変更を表示します。オーナーはそれをリセットできます。

ステップ 2-2 で、意図、オーナーによる調整、暗黙のフィードバックを次のように作りました。

- 意図: 開いている意図は最大 5 件です。それぞれ 1 から 168 時間続き、既定は 24 時間です。1 件ごとに話したい気持ちを 0.2 足し、上限は 0.4 です。状況ブロックが id 付きで一覧を示し、モデルは使った意図を終えます。ミッションと同じく、IndexedDB に保存します。
- オーナーによる調整: `quiet` は、自律発話を 1 から 720 分止めます。`less` と `more` は、待機中の間隔を一時的に 1.5 倍か 0.67 倍にします。0 分のときは、設定の間隔そのものを変えます。`normal` は、時間付きの変更をすべて終えます。変更は端末に保存するので、再起動しても続きます。
- 話す量のツールは、オーナーのメッセージに答えるターン以外では断ります。ツールの一覧はどのターンでも同じなので、ツールがターンを確かめます。
- 暗黙のフィードバック: オーナーのメッセージがないまま自律発話をするたびに、待機中の間隔を 1.3 倍にします。上限は設定の 3 倍です。待機中の発話だけに効きます。回数はメモリにだけ持つので、再起動すると元のペースに戻ります。
- 設定画面は、時間付きの変更を表示し、リセットできます。暗黙のフィードバックは、ステップ 2-3 のインスペクターが表示します。その回数を持つのがリーダーだけだからです。
- モデルがツールで気分を動かす機能は、まだ入れません。効果が小さいので、必要になるまで待ちます。

### プロンプトの予算

コードは、毎回同じ形でリクエストを組み立てます。各部分に上限があります。

| 部分 | 上限 | 備考 |
| --- | --- | --- |
| 人格(システムプロンプト) | 固定 | 変わらないため、プロバイダーのキャッシュが効きます。 |
| オーナーのプロフィールの要約 | 約 300 トークン | |
| 思い出した記憶 | 上位 5 件、約 500 トークン | 記憶の索引の全件は入れません。 |
| 状況ブロック | 約 300 トークン | モード、最後の発話からの経過時間、発話の型のヒント、直近の発話 |
| タイムライン | 直近 10 件 | |
| ミッションの指示文 | 実行中の 1 件、最大 500 文字 | |
| 会話履歴 | 要約で上限内に保つ | |
| 画像 | フレームポリシーが決める | |

- リクエストが上限を超えたら、コードは優先度の低い部分から削ります。
- 詳しい情報は、モデルがツールで読みます。コードは事前にプロンプトへ入れません。
- IO トレースは、各部分の大きさを記録します。トレースを見れば、プロンプトが情報を詰め込みすぎているかが分かります。

ステップ 2-4 は、プロンプトの予算を次のように作りました。自律ターンだけでなく、すべてのチャットのリクエストが対象です。

- 履歴の要約: 要約の後ろのメッセージが 60 件または約 40,000 文字を超えたら、セッションのチャットモデルが、直近 20 件を除くすべてを、最大 1,500 文字の新しい要約にまとめます。リクエストは、要約とその後ろのメッセージを送ります。要約は大きな段階で進むので、キャッシュされる先頭部分が変わるのは数十件に 1 回です。
- 要約は、送信の後に裏で動きます。使用量の用途は `history-summary` です。要約ができるまでは、リクエストは全履歴を送ります。チャットの画面には、常にすべてのメッセージが表示されます。
- 端末のセッションのメタ情報が、要約とその最後のメッセージを持ちます。そのメッセージが削除されると要約は合わなくなるので、新しい要約ができるまで、リクエストは全履歴を送ります。
- 設定 > モジュール > 短期記憶 で、要約のオンとオフを切り替えます。開いている会話の要約の表示と削除もできます。既定はオンです。
- 記憶: 索引は最大 50 件で、カード自身の記憶が先、それぞれ新しい順です。`builtIn_searchMemory` が、ほかの記憶を 2 文字単位の一致で探します。日本語でも働きます。意味で上位 5 件を想起するには埋め込みが必要なので、記憶の ADR で作ります。
- IO トレースは、システムプロンプト、記憶の索引、要約、履歴の文字数と、要約にまとめたメッセージの件数を記録します。
- オーナーのプロフィールはまだないので、その部分はありません。タイムラインとミッションの指示は、それぞれのステップで追加します。

### 知覚

- キャプチャは端末上で動き、コストはかかりません。リングバッファが、直近 60 秒のフレームを最大 2 fps で保持します。メモリ上だけに置きます。
- 対象ウィンドウを持つミッションは、そのウィンドウだけをキャプチャします。対象ウィンドウが前面にないときは、知覚は一時停止します。
- web 版では、1 つのウィンドウか 1 つのタブを共有することを推奨します。
- 検出器は、モデルを呼ばずにコードで動きます。画面の変化、動きの量、大きな音、アプリの切り替え、長い静止を報告します。
- どの検出器も特定のゲームを知りません。各検出器のイベントには、顕著度の値があります。
- バッファはプロンプトに含めません。フレームがモデルに届くのは、判断ターンのときだけです。

次のルールで、メニュー、画面遷移、デスクトップへの切り替えが大きな出来事として数えられるのを防ぎます。

- **落ち着いてから比べる。** 大きな変化の後、検出器は画面が 0.5〜1 秒静止するまで待ちます。その後、新しい静止画面を、前の静止画面と比べます。
- **見慣れた画面。** 検出器は、最近の静止画面ごとに小さなハッシュを持ちます。最近の画面に近い画面は、顕著度が低くなります。メニュー、マップ、デスクトップは見慣れた画面になります。
- **アプリごとの基準。** 検出器は、固定値ではなく、今のアプリの普段の変化量を基準に変化を測ります。
- **アプリ切り替えの滞在時間。** アプリの切り替えは、オーナーが新しいアプリに数秒留まった後で数えます。デスクトップやファイルマネージャーへの切り替えは、顕著度が低くなります。
- **モデルが付けるラベル(後で)。** モデルは、タイムラインのメモで画面にラベルを付けられます。例は「メニュー」です。その後、検出器はその画面の顕著度を低くします。

ステップ 3-1 は、画面の取り込み口、リングバッファ、プライバシーの決まりを次のように作りました。まだ、モデルにフレームは送りません。

- **画面の取り込み口。** 各アプリは、知覚のランナーに `ScreenSource` を渡します。取り込みを始め、前面のウィンドウと、ロックやスリープを伝えられます。
  - デスクトップアプリは、`electron-screen-capture` を通して、プロンプトなしで主ディスプレイを取り込みます。
  - main プロセスは、eventa の invoke `electronForegroundWindow` を通して、`get-windows` 9.3.0 で前面のウィンドウを読みます。Electron には、それを知る方法がありません。バージョン 10 は、リポジトリの `minimumReleaseAge` の決まりには新しすぎました。
  - web アプリは `getDisplayMedia` を使います。ページを開くたびに、開始にはオーナーのクリックが必要です。選択画面はウィンドウを先に示し、AIRI のタブを外します。スマホのブラウザーには対応しません。
- **リングバッファ。** レンダラーのリーダーが、毎秒 2 フレームを取り、直近 60 秒、最大 120 フレームをメモリーだけに持ちます。
  - 各フレームは、長い辺が最大 1280 ピクセルの JPEG と、検出器のための 64×36 のグレースケールの縮小版です。ワーカーがフレームを変換します。
  - 一時停止、ロック、リーダーの交代、共有の終わりで、フレームを捨てます。
- **プライバシー。**
  - 設定 > モジュール > 画面の知覚 でオンにします。既定はオフです。
  - 知覚がオンの間、デスクトップアプリのコントロールアイランドとチャットのヘッダーに、目のボタンが出ます。1 クリックで一時停止と再開をし、一時停止は再起動の後も続きます。
  - 除外リストは、前面のウィンドウのアプリ名、アプリのファイル名、ウィンドウのタイトルに合わせます。合うと、フレームを取る前に飛ばします。英語の項目は、単語全体が合うときだけ合います。
  - 既定のリストには、パスワードマネージャー、メッセンジャー、銀行の語が入っています。web アプリは前面のウィンドウが分からないので、設定はウィンドウかタブを 1 つ共有するよう勧めます。
  - 画面のロックかスリープで、オーナーが戻るまで取り込みを止めます。共有がなくなると取り込みは終わり、オーナーがもう一度始めます。
- **インスペクター。** 状態のストアが、状態、フレーム数、前面のアプリ、飛ばしたフレームの数を、すべてのウィンドウに伝えます。ウィンドウのタイトルは含めません。

ステップ 3-2 は、検出器を次のように作りました。その出来事は、まだ圧力につなぎません。

- `packages/stage-shared` の `ScreenDetector` は、64×36 の縮小版、時刻、前面のアプリを読みます。リーダーの知覚のランナーで動き、モデルは呼びません。
- **フレームの差。** フレームの間の明るさの差の平均で、0〜1 です。
- **動きの量。** フレームの差の移動平均で、半減期は 5 秒です。出来事ではなく、値です。ステップ 3-5 の実況が、話す間隔に使います。
- **落ち着いてから比べる。** 差が 0.01 以上のフレームで、動きが始まります。静かなフレームが 2 つ（1 秒）続くと、画面は落ち着きます。そのとき、新しい静かな画面を、前の静かな画面と比べます。差が 0.02 以上なら、`scene-change` の出来事です。
- **ノイズの床。** ずっと動き続ける画面、たとえばアニメーションするゲームのロビーは、決まったしきい値では落ち着きません。デスクトップでの確認でそれが分かりました。そこで検出器は、ふだんのフレームの差を追います。上がるときの半減期は 15 秒、下がるときは 2 秒です。この床の 1.5 倍より小さいフレームを静かとし、場面の変化は床の 2 倍以上を必要とします。
- **見慣れた画面。** 検出器は、直近の 32 の静かな画面の 64 ビットの差分ハッシュを持ちます。新しい画面がそのどれかと 6 ビット以内なら、顕著度を 0.3 倍にします。
- **アプリごとの基準。** 各アプリは、場面の変化の移動平均を持ちます。最初は 0.05 です。顕著度は、基準を超えた変化を、基準の 3 倍で割った値です。web では、すべてのフレームが 1 つの基準を使います。
- **アプリ切り替えの滞在時間。** デスクトップでは、オーナーが新しいアプリに 5 秒いると、`app-switch` の出来事が来ます。デスクトップ、ファイルマネージャー、AIRI への切り替えの顕著度は 0.2、ほかは 0.5 です。切り替えそのものの画面の変化は、場面の変化にしません。
- **長い静止。** 3 分変わらない画面は、顕著度 0.1 の `still` の出来事を 1 回出します。
- **除外されたフレーム。** 飛ばしたフレームの後、検出器は落ち着きをやり直し、前の画面とは比べません。除外されたウィンドウのアプリは、検出器に伝わりません。
- **大きな音は待ちます。** アプリは、まだ音を取り込んでいません。システムの音には通話の友だちの声も入り、ADR は 1 つのプロセスの音だけを取り込みます。そのネイティブモジュールはステップ 5 のゲームの音で作るので、大きな音の検出器もそこで作ります。
- `DETECTOR_LIMITS` がしきい値を持ちます。最初の値は合成したフレームの列で決め、ステップ 3-6 のリプレイ評価で調整します。
- インスペクターは、動きの量と、最近の 20 の出来事を表示します。時刻、種類、顕著度、アプリ、見慣れた画面かどうかです。

ステップ 3-3 は、フレーム付きの判断ターンを次のように作りました。

- **圧力としての出来事。** 画面の各出来事は、その顕著度で `perceived` の出来事としてポリシーに入ります。判断の後の顕著な出来事は、これまでどおり、その発話を古くします。
- **`fresh-keyframes`。** `packages/stage-shared` の `pickFreshKeyframes` は、最新のフレーム、前のターンからの各出来事の近くで最も大きな変化の直前のフレーム、そして最も変化したフレームを選びます。同じに見えるフレームは飛ばします。リプレイ評価が選ぶまでの既定です。
- **ターンのフレーム。** 駆動のターンは、選んだフレームを一時的な通知に添付します。最新のフレームは 1280 ピクセル、古いフレームは 512 ピクセルです。一時的な通知は保存されず、その添付もチャットのアセットの保存先に入らないので、フレームはディスクに届きません。あいさつとおかえりにはフレームを付けず、除外したウィンドウが前面にある間も送りません。
- **状況ブロック。** 通知は、各フレームの古さ、タイトルを除いた前面のアプリ、前のターンからの画面の出来事を最大 5 つ伝えます。画面の文字は他のアプリのデータで、指示ではないと伝えます。
- **画像の予算。** 設定 > モジュール > 画面の知覚 で、1 時間あたりの画像を決めます。既定は 20 枚です。端末が送った時刻を持ち、予算は直近 60 分の窓で数えるので、毎正時の直後にまとめて送ることは起きません。予算が半分を切ると、ターンは最新のフレームだけを送り、出来事の圧力は `max(0.25, 残りの割合 / 0.5)` になります。予算が残っていないと、ターンはフレームなしで行い、通知がそれを伝えます。
- **画面のターンのツール。** フレーム付きのターンでも、コードはミッションのツールを出します。画面の文字が指示として働く既知のリスクは、既知のリスクの表のとおり、まだ残ります。今は、通知が画面の文字をデータとして示すだけです。

### フレームポリシー

フレームポリシーは、各ターンでモデルに送るフレームを選びます。差し替えられる部品です。開発者向けの設定で選び、既定はリプレイ評価で決めます。

| ポリシー | フレーム |
| --- | --- |
| `fresh-keyframes` | 前回のターン以降で最も変化したフレームと、出来事の直前のフレーム。最新のフレームだけを元のサイズにします。 |
| `contact-sheet` | 時刻付きの縮小フレームを、タイル状に並べた 1 枚の画像。予算は 1 枚として数えます。 |
| `scene-anchor` | 場面ごとに 1 枚の基準フレームを、プロンプトの固定部分に置きます。新しいフレームはその後に続きます。 |

- ポリシーは組み合わせられます。例は、`scene-anchor` と `contact-sheet` の組み合わせです。
- `scene-anchor` には、プロバイダーのキャッシュが必要です。既定モデルのキャッシュ読みの料金は、入力の料金の約 1/50 です。画像にキャッシュが効くかは、まだ誰も測っていません。
- フレームで運べない内容は、場面の状態のメモが運びます。モデルがこれを更新します。例は、ゲーム、場所、目的、プレイヤーキャラクターの体力です。

### 画像予算

- オーナーは、1 時間あたりの画像枚数で予算を設定します。既定は低くします。
- 予算は、見張りの確認を含め、モデルに送るすべての画像を数えます。
- 予算が少なくなると、コードは判断ターンの間隔を延ばします。予算が尽きると、直近 60 分の窓に空きができるまで画像は送られません。
- 実行中の実況ミッションは、予算を引き上げます。
- 設定画面に、現在の 1 時間で送った画像枚数を表示します。

### 用途ごとの使用量

各モデル呼び出しは、その用途を記録します。設定画面とインスペクターが、用途ごとの使用量を表示します。

- 用途は、オーナーへの返答、自律ターン、実況、見張りの確認、話題の種、記憶の処理、モーション生成です。
- 用途ごとに、呼び出し回数、入力トークン、出力トークン、画像、トークンの報告がない呼び出しを記録します。
- 費用とキャッシュされたトークンは記録しません。正確な費用は、オーナーがプロバイダーのサイトで確認します。2026-11-01 にオーナーが決めました。
- 表示は、今日と直近 30 日です。

ステップ 2-3a は、使用量の記録を次のように作りました。

- LLM ストアが、終わったストリームごとに記録します。ツールのラウンドがあるストリームは、ラウンドごとに 1 回と数えます。失敗またはキャンセルしたストリームは、トークンなしの 1 回と数えます。
- 用途は `owner-reply`、`initiative`、`mission`、`task`、`scene`、`vision`、`voice-assist`、`tool-card`、`artistry`、`other` です。チャットストアは、ターンの用途を通知の source から読みます。実況、見張りの確認、話題の種、記憶の処理、モーション生成の用途は、それぞれのステップで追加します。
- IndexedDB は、日・用途・モデルごとに 1 件の記録を 30 日間持ちます。記録は端末に残り、同期しません。
- 設定 > 使用量 が、今日と直近 30 日の、用途ごとのトークン量を表示します。

### インスペクター

インスペクターは、メインのステージ画面に重ねるパネルです。開発者向けの設定でオンにします。キャラクターが話す理由と黙る理由を表示します。

- 欲求、閾値、内的状態を、時間に沿ったグラフで表示します。
- 今のゲートの理由、モード、実行中のミッション、意図、話題の熱を表示します。
- タイムライン、場面の状態、最後のターンのフレーム、用途ごとの使用量を表示します。
- 有効なオーナーの調整を表示し、それをリセットできます。
- パネルは状態を読むだけです。ポリシーは変えません。

ステップ 2-3b は、インスペクターを次のように作りました。インスペクターの置き場所を変えました。

- インスペクターは、ステージに重ねるパネルではなく、devtools のページです。デスクトップのメインウィンドウは小さくて透明なので、パネルはモデルを覆いました。設定ウィンドウなら、モデルの横にページを表示できます。両方のアプリで、設定 > 開発者 から開きます。
- `core-agent` の `initiativeReadout` が、欲求とその内訳、閾値、内的状態、ゲートの理由、不応期、反応のない発話の数、間隔の倍率、予算を読みます。判断はしません。
- ポリシーの状態を持つのはリーダーだけです。ページが見ている間、runner は毎秒、同期ストアを通して値を公開します。ページは 5 秒ごとに見ていることを知らせるので、ページを閉じると公開は止まります。
- ページは、直近 10 分の欲求と閾値を描きます。開いている意図、実行中のミッション、リセット付きのオーナーの調整、今日のトークン量も表示します。
- 話題の熱、タイムライン、場面の状態、フレームは、ステップ 2b と 3 で追加します。

### 発話の圧力

- イベントは、顕著度に応じて圧力を加えます。圧力は時間とともに減衰します。長い沈黙は、退屈の項を加えます。
- 顕著度は二乗で効きます。小さな画面変化が多くても、大きな変化 1 回より加わる圧力は小さくなります。
- 各モードには、基本の閾値があります。ターンとターンの間の 1 サイクルごとに、閾値のランダムなゆらぎを 1 回引くため、ターンの間隔はばらつきます。
- 各ターンの後には、不応期があります。黙ると決めたときは、圧力の一部だけを下げます。
- ゲートは、オーナーが入力中または発話中のとき、音声の再生中、ターンの実行中に、ターンを止めます。オーナーの入力が常に優先です。
- 判断から再生までの間に、顕著なイベントが起きたら、コードは古くなった発話を捨てます。
- オーナーは、基本間隔、静音時間、1 日の予算を設定します。既定は控えめです。

### 判断ターン

- 圧力が閾値を超えたら、コードが発話モデルを呼びます。
- リクエストは、プロンプトの予算に従います。フレームポリシーが選んだフレーム、タイムライン、場面の状態、内的状態のヒントを含めます。
- イベントの後には、リクエストにイベント直前のフレームを含められます。遅れたリアクションでも、原因を見て話せます。
- 画像は、このリクエストだけに含まれます。履歴には、発話のテキストとタイムラインのメモが残ります。
- モデルは、話すか、黙ります。マーカーで、タイムラインのメモを書く、場面の状態を更新する、こともできます。ツールで、意図を書けます。

画面なしの判断ターンは、次のように動きます。ステップ 2-1 で作りました。

- レンダラーのリーダーが、毎秒ポリシーに尋ねます。ターンになると、オーナーが開いている会話に、一時的な通知を送ります。
- 通知は状況ブロックです。理由、時間帯、最後のメッセージからの時間、発話の型のヒント、最近の自律発話 3 件を伝えます。
- 通知を読むのは、そのリクエストだけです。履歴には返答だけが残るので、黙ったターンは跡を残しません。
- ゲートは 4 つの状態を読みます。オーナーの文字入力、オーナーの音声入力、発話の再生、実行中のチャットのターンです。
- 各入力欄は、小さな同期ストアで入力中を知らせます。そのため、リーダーはどのウィンドウでの入力も分かります。入力中は、最後の入力から少なくとも 15 秒と、IME の変換の間ずっと続きます。入力欄が空になると終わります。
- ターンの途中でオーナーが入力するか、話すか、メッセージを送ると、コードはそのターンを止めます。ターンは `dropped` で終わります。話したい気持ちは残るので、オーナーが止まると、キャラクターはその時の状況で話し直します。

### 実況

実況のペースは、決まった間隔ではなく、場面に従います。

- 活発な場面では退屈が速くたまり、静かな場面では遅くたまります。静かな場面では、長く黙っていられます。
- 実況の 1 回の発話は、1 文程度の短さです。長い発話は、次の出来事に間に合いません。
- 大きな出来事が起きたら、コードはすぐに次のモデル呼び出しを始めます。新しい発話は、少ない遅れで今の発話と入れ替われます。

新しい出来事は、今の発話に割り込めます。次のルールで、話の筋を保ちます。

- 割り込みには、非常に大きな出来事が必要です。その顕著度は、今の発話のきっかけの顕著度より、明らかに大きくなければなりません。
- 通常の割り込みでは、今の文を言い終えてから、残りを捨てます。最も大きな出来事だけが、発話をすぐに切ります。
- 割り込みの後、約 15 秒は次の割り込みをしません。
- オーナーの発話は、常にキャラクターを止めます。キャラクターがオーナーに割り込むことはありません。
- タイムラインは、割り込まれた発話を記録します。キャラクターは、後でその話に戻れます。

### タイムラインと場面の状態

- タイムラインは、時刻付きの短いメモのリストです。
- コードは、アプリの切り替え、オーナーの発話、ミッションの開始、割り込みを書き込みます。モデルは、見たことを書き込みます。例は「ボス戦が始まった」です。
- 古いメモは要約して、リストを短く保ちます。
- タイムラインは、画面で起きたことの唯一の履歴です。
- 場面の状態は、モデルが更新する 1 つの短いテキストです。履歴ではなく、今の場面を表します。

ステップ 3-4 は、タイムラインと場面の状態を次のように作りました。

- **ツールではなくマーカー。** モデルは、ステップ 2b-2a の話題のラベルと同じように、返事の中に `<|NOTE 短い事実|>` と `<|SCENE 今の場面|>` を書きます。ツールだと、モデルがツールの結果の後にもう一度答えるので、ターンごとにモデル呼び出しが 1 回増えます。オーケストレーターは、黙った返事でも、マーカーを `onTimelineMarker` で伝え、発話とプラグインには渡しません。1 つの返事のメモは最大 2 つです。
- **コードのメモ。** 知覚が動いている間、コードは、アプリの切り替え、オーナーのメッセージ（中身は書きません）、ミッションの開始と終了を書きます。割り込みはステップ 3-5 で足します。
- **保存。** 各会話は、端末の IndexedDB に自分のタイムラインを持ちます。画面の内容なので、同期しません。会話を消すとそのタイムラインも消え、モジュールのリセットですべてのタイムラインが消えます。
- **上限。** メモは 120 文字、場面は 300 文字です。メモが 30 件を超えたとき、または 12 時間より古いメモがあるとき、チャットモデルが、使用量の用途 `timeline` の裏の呼び出しで、古いメモを前の要約と一緒に要約します。
- **プロンプト。** 画面付きの駆動のターンは、場面、要約、最新の 12 件のメモを渡し、マーカーを頼みます。オーナーへの返信には、まだタイムラインを渡しません。
- インスペクターは、開いている会話の場面、要約、最新のメモを表示し、消去できます。

### 内的状態と多様性

- 内的状態は、エネルギー、気分、退屈、好奇心、意図、直近の発話の記録です。コードが、時間、イベント、ツールから更新します。
- 発話の型は、反応する、茶化す、質問する、記憶を思い出す、独り言を言う、静かに観察する、のどれかです。コードが重みを付けて型を抽選します。
- 最近使った型は、重みが下がります。
- コードは、抽選した型を、同じ呼び出しの中で軽いヒントとして渡します。決まった割合のターンでは、ヒントを渡しません。モデルはヒントを無視できます。
- リクエストには、キャラクターの直近の発話を含めるため、モデルは同じ書き出しと構造を避けます。
- この設計は、2 段目の LLM を追加しません。

### ミッション

ミッションは 3 つの層を持ちます。

| 層 | 内容 | 作る人 | 増え方 |
| --- | --- | --- | --- |
| 部品(コード) | トリガー、レンズ、話し方、終わり方、予算 | 開発者 | まれ。新しい種類のトリガーだけがコードを必要とします。 |
| テンプレート(データ) | 部品の組み合わせと、短い指示文 | オーナー。モデルが提案し、オーナーが承認することもできます。 | 使うほど増える |
| インスタンス | 値の入ったテンプレート。例は、時刻や対象ウィンドウ | モデルが、オーナーの言葉からツールで作る | 依頼ごとに 1 つ。終われば終わる |

部品:

- **トリガー:** 時刻、画面の条件、アプリの起動、オーナーの依頼。
- **レンズ:** 対象ウィンドウ、注目する領域、何を見るか。
- **話し方:** モード、`mustSpeak`、1 回の発話の長さ。
- **終わり方:** 1 回の実行の後、対象ウィンドウが閉じたとき、条件が成り立ったとき、制限時間。

テンプレートは、`mission` ブロックを持つレシピです。レシピのキーワード、承認、提案、保存、設定画面を使います。
レシピは、声を出さずに裏で動きます。ミッションは、声を出して前面で動くため、独自の実行経路を持ちます。

組み込みのテンプレート:

| テンプレート | トリガー | レンズ | 話し方 | 終わり方 |
| --- | --- | --- | --- | --- |
| `reminder` | 時刻 | なし | `mustSpeak` | 1 回の実行の後 |
| `commentary` | オーナーの依頼 | 対象ウィンドウ | 実況モード | 対象ウィンドウが閉じたとき |
| `watch` | 画面の条件 | 対象ウィンドウと領域 | `mustSpeak` | 条件が成り立ったとき |
| `small-talk` | オーナーの依頼、または近くにいる静かなオーナー | なし | 普段のモードで、より頻繁に | オーナーが離れたとき、止めると言ったとき、制限時間 |
| `greeting` | アプリの起動 | なし | 通常 | 1 回の実行の後 |
| `welcome-back` | 離席後のオーナーの入力 | なし | 通常 | 1 回の実行の後 |

最後の 2 つのテンプレートが、1 日のリズムを作ります。次のルールがそれを補います。

- あいさつは、ローカルの時刻と、最後に話してからの時間で変わります。何日も空いた後の最初の会話は、別のあいさつになります。
- 時間帯が内的状態を変えます。深夜はエネルギーが低くなり、発話のヒントも時刻で変わります。
- デスクトップ版は、システムのアイドル時間から離席を読み取ります。web 版は Idle Detection API を使い、それが使えないときはページのフォーカスを使います。

ステップ 2b-1 は、1 日のリズムを次のように作りました。話題と雑談は、ステップ 2b-2 で作ります。

- あいさつとおかえりは、ミッションのテンプレートではなく、コードの中のリズムのターンです。インスタンスがいらないからです。レシピとしてのテンプレートは、オーナーやモデルがテンプレートを作るときまで待ちます。
- `core-agent` の `requestRhythmTurn` が、欲求と閾値を使わずにそれを始めます。不応期では止まりませんが、オーナーの入力、読み上げ、実行中のターン、頼まれた静けさ、静かな時間帯、1 日の上限では止まります。ゲートに 2 分止められたリズムのターンは捨てます。
- あいさつ: リーダーの最初のティックで、開いている会話が 3 時間以上静かだったら、あいさつします。通知は、時間帯と、最後のメッセージからの時間を伝えます。
- おかえり: 10 分間入力がないと、オーナーは離席中になります。画面ロックかスリープでは、すぐに離席中になります。30 分以上の離席から戻ると、おかえりを言います。ただし、ほかのリズムのターンから 10 分以内なら言いません。通知は、離れていた時間を伝えます。
- デスクトップ版は、eventa の invoke で `powerMonitor.getSystemIdleTime()` を 15 秒ごとに読みます。web 版は、ページの入力と表示状態だけを数えます。Idle Detection API は許可を求めるからです。
- 夜は 22:00 から 05:00 です。夜は閾値が 1.5 倍になります。冗談と質問の重みが下がり、独り言と静かなひとことの重みが上がります。
- 設定 > モジュール > 自律発話 で、あいさつとおかえりのオンとオフを切り替えます。既定はどちらもオンです。インスペクターは、オーナーが離席中かどうかと、最後のリズムのターンを表示します。

- コードは、モデルが渡す各値を検証します。モデルができるのは、インスタンスの作成と停止だけです。
- ミッションの指示文は最大 500 文字です。人格を置き換えることはありません。
- 前面のミッションは、同時に 1 つだけ動きます。例は、実況か雑談です。リマインドや見張りのような裏のミッションは、発火したときだけプロンプトに入ります。
- 通知に `mustSpeak` オプションを追加します。現在の通知は、モデルが可視の返答を返さないと黙るため、リマインドを運べません。
- 見張りは、発話ターンではなく確認ターンを使います。領域の変化か、遅いタイマーが確認を始めます。
- 確認ターンでは、モデルは小さな切り抜きを受け取り、ツールで答えます。「はい」のときだけ、`mustSpeak` の通知を始めます。
- IndexedDB は、インスタンスを端末上に、1 件ごとに 1 レコードで、レシピのレコードと同じ形で保持します。
- レンダラーのリーダーが時計を確認します。

#### ミッションのツール

- `builtIn_startMission` は、テンプレートの名前とその値を受け取ります。`builtIn_listMissions` はインスタンスを一覧にします。`builtIn_stopMission` は 1 つのインスタンスを止めます。
- ツールの説明は、テンプレートとその値を、プロンプトの予算の中で短く並べます。
- 各テンプレートは、独自の値のスキーマを持ちます。値が誤っていれば、ツールは理由を返し、モデルはやり直せます。
- 新しいテンプレートに、新しいツールは要りません。

#### リマインドのルール

- モデルは、最初の実行を次の 2 つの形のどちらかで指定します。
  - `at`: ローカル時刻の ISO 文字列。例は `2026-10-31T18:00` です。
  - `after`: 今からの分数。例は「10 分後」です。
- `after` の開始は、コードが実際の時刻から秒まで数えます。モデルに見えるメッセージの時刻には秒がありません。そのため、モデルが自分で数えた時刻は、最大 1 分早いか、すでに過去です。
- ツールの説明は、今からの時間には `after` を使い、`at` はオーナーが時刻を名指ししたときだけ使うよう、モデルに伝えます。
- コードは、過去の時刻と遠すぎる未来の時刻を拒否します。現在の分の時刻は有効です。
- リマインドは 1 回だけ実行するか、次のどちらかで繰り返します。
  - 1 つの時刻で、毎日、平日、または選んだ曜日に毎週。
  - 最初の実行からの間隔で。間隔は 15 分から 24 時間です。より短い間隔では、キャラクターが話しすぎます。
- 繰り返しのリマインドは、各実行の後にコードが次の時刻を設定します。オーナーは、ミッション一覧かチャットでそれを止めます。
- 繰り返しのリマインドはオーナーがチャットで頼むため、承認は要りません。これは、ADR 2026-10-10 の繰り返しレシピのルールと異なります。
- リマインドは、静音時間中も一時的に静かにしている間も話します。オーナーが時刻を選んだため、時刻が優先です。

`mustSpeak` の通知にモデルが可視の返答を返さない場合も、コードはオーナーにリマインドが届くようにします。

1. コードは、通知をもう 1 回だけ送ります。
2. 2 回目の返答も空なら、キャラクターは決まった文を話します。例は「リマインド: 薬の時間」です。
3. モデルの呼び出しが失敗した場合、コードは 2 回目を省き、すぐに決まった文を話します。
4. 発話の再生が失敗した場合、コードは OS の通知を表示します。web 版では、そのために通知の許可が必要です。

アプリが閉じていた場合は、次の起動で見逃したリマインドを伝えます。

- 期限より短い時間だけ見逃したリマインドは、通知を受けます。既定の期限は 24 時間で、設定画面で変えられます。
- それより古い見逃したリマインドは、ミッション一覧で「見逃し」の状態になるだけです。
- 1 回の起動での見逃したリマインドは、すべて 1 つの通知にまとめます。起動の後に、キャラクターが何度も話さないためです。

### 雑談

話題は流れます。コードは、会話全体に 1 つの話題を割り当てません。

- **話題の種。** 池が、記憶、オーナーの関心、最近の画面の出来事、季節、意図、キャラクターの関心から種を集めます。安い裏の呼び出しが種を足すこともできます。
- **各ターンの選択。** モデルは、今の流れを続ける、直前の発話から関連する話題へ移る、新しい種を選ぶ、のどれかを選べます。コードは種を 2〜3 個示します。
- **新しさ。** 最近の話題に近い種は、重みが下がります。
- **熱。** 各話題の流れには熱があり、ターンごとに下がります。オーナーの反応が少ないと、より速く下がります。例は、短い返事、返事がない、質問が返ってこない、です。
- **流れの終わり。** 冷めた流れは、選択肢から外れます。コードは、関連する話題と新しい種を示します。
- **話題の履歴。** 各ターンは、短い話題のラベルとその埋め込みを記録します。池は、同じ日と最近の日の話題を避けます。

ステップ 2b-2a は、すべての自律発話の話題を次のように作りました。`small-talk` テンプレートは次に作ります。

- **話題のラベル。** 通知は、発話の最後に `<|TOPIC 数語|>` を書くように頼みます。オーケストレーターは、スタンプのマーカーと同じように、ラベルを返信の `topic` に保存します。ラベルは話されず、表示もされません。モデル呼び出しも増えません。
- **話題の履歴。** ランナーは、開いている会話の、直近 3 日の自律発話を読みます。各行は、そのラベルを使います。ラベルがない行は、本文を使います。専用の保存先はいりません。
- **流れと熱。** 近さが 0.5 以上で続く行を、1 つの流れとします。オーナーが返事をした行は、熱を 0.85 倍にします。返事のない行は、0.55 倍にします。0.35 以下で流れは冷め、通知は新しい話題を頼みます。
- **種。** 池には、カードの記憶の索引の行と、暦の種が入ります。暦の種は、月、曜日、月や年の初めと終わりです。コードは、重みで種を最大 3 個引きます。最近の話題に近い種は重みが下がり、近さが 0.6 以上の種は出しません。発話したターンで出した種は、6 時間休ませます。2 文字の組の近さは、行と言語が違う種を見逃します。たとえば、英語の暦の種と日本語の行です。休ませることで、その種が毎ターン戻るのを防ぎます。休みはメモリーだけに持ちます。
- リズムのターンには、種を出しません。そのターンには、それぞれの理由があるからです。意図は、通知の中の意図の一覧のままです。画面の出来事はステップ 3 で、オーナーの関心、キャラクターの関心、種の呼び出しは後で足します。
- **近さ。** コードは、共通する 2 文字の組の割合で話題を比べます。これは仮の段階です。クライアントには、まだテキストの埋め込みがありません。近さは、ホストが差し替えられる関数です。記憶の ADR が埋め込みを足したら、保存済みのラベルを埋め込みにし、埋め込みの近さを 2 文字の組の代わりに使います。
- **多様性。** `core-agent` は、`distinct-2`、発話タイプのエントロピー、続く話題どうしの近さを計ります。インスペクターは、流れ、前のターンの種、今日の行の多様性を表示します。今日の発話タイプはメモリーだけに持つので、再起動で数え直します。

ステップ 2b-2b は、`small-talk` テンプレートを次のように作りました。

- **テンプレート。** `small-talk` は、`reminder` と同じく、コードに組み込んだテンプレートです。ステップ 2b-1 の判断のとおり、レシピとしてのテンプレートはまだ待ちます。
- **きっかけ。** オーナーの依頼だけが始めます。モデルが `builtIn_startMission` で 5〜120 分の雑談を始めます。オーナーが時間を言わないときは 30 分です。「静かなオーナーが近くにいるとき」は待ちます。ふだんの自律発話に近く、依頼なしに頻度を上げると、オーナーがうるさく感じるおそれがあるからです。[アイデアのメモ](../context/autonomy-ideas.ja-JP.md) に残します。
- **ゲート。** 自律発話がオフのときと、別の雑談が動いているときは、コードが断ります。今のところ、前面のミッションは雑談だけです。
- **話し方。** 実行中は、話す間隔が 2 分、ターンの後の休止が 45 秒です。オーナーの一時的な倍率（たとえば「少し話を減らして」）は、そのままかかります。返事のない発話で間隔が延びる仕組みも残ります。1 日の上限と静かな時間帯は守ります。通知は、雑談中であることと残り時間を伝えます。話題は、ステップ 2b-2a のとおりに動きます。
- **終わり方。** ミッションランナーが時間切れで終わらせます。オーナーが止めてと言うと、`builtIn_stopMission` で終わります。オーナーが離席すると、ステップ 2b-1 の離席の検出から、イニシアチブのランナーが終わらせます。静かにしての依頼でも終わります。インスタンスは、理由（`time`、`owner`、`away`、`quiet`）を持ちます。
- **インスタンス。** `MissionInstance` は、テンプレートの共用体です。雑談の状態は `running` で、時間切れなら `done`、それ以外は `stopped` で終わります。再起動の後、時間切れ前の雑談は続きます。
- **ツールの値。** `builtIn_startMission` の値は、リマインダーの値か雑談の値（`anyOf`）です。リマインダーの値は変えていません。新しいテンプレートに、新しいツールはいりません。

### 身体: モーション

オーナーは、外部の人型 VRM モデルを使います。ボーンや表情はモデルごとに異なります。

- 読み込み時に、コードはモデルが持つヒューマノイドボーンと表情を調べます。
- 足りない部位を必要とするクリップやマーカーはスキップします。足りない機能はエラーを出さずにオフになります。
- `.vrma` クリップは正規化されたヒューマノイドボーンを使うため、1 つのクリップが多くのモデルに適合します。

MMD モデルも同じ `.vrma` クリップを使います。ライブラリは `.vrma` のデータだけを保存し、MMD モデルが再生するときにコードがリターゲットします。

- VRM の各ボーンに、MMD の標準ボーンを対応させます。例は `leftUpperArm` と `左腕` です。モデルにないボーンの回転は、子のボーンに引き継ぎます。
- VRM の回転は T ポーズが基準です。コードは、多くのモデルで A ポーズである MMD の基準の姿勢に合わせて補正します。
- 腰の移動は、腰の高さの比率に合わせて `センター` を動かします。
- コードは、リターゲットした姿勢から `左足ＩＫ` などの IK ボーンの位置も書き込みます。IK はオンのままなので、脚を IK で動かす VMD モーションと混ぜられます。
- オーナーが VMD の待機モーションを選ぶまで、MMD モデルは VRM の待機ループを再生します。
- リターゲットは `packages/stage-ui-mmd/src/utils/vrma-retarget.ts` が担当します。生成したクリップも同じリターゲットを通ります。

3 つの層を重ねます。次の順に作ります。

1. **手続き生成の層。** コードは、クリップなしで体を動かします。呼吸、小さな揺れ、首と頭が遅れて付いてくる視線を加えます。モデルが考えている間は視線が外れ、音声の振幅がうなずきを動かします。まばたきと目の動きは既にあります。
2. **ライブラリ。** モデルは、既存の `<|ACT|>` マーカーに、表情と自由文のモーションを書きます。例は `<|ACT {"expression":"shy","motion":"scratch head shyly"}|>` です。コードは、ライブラリから最も近いクリップを再生します。
3. **生成モーション。** 生成が、時間をかけてライブラリにクリップを足します。

ライブラリ:

- IndexedDB は、クリップごとに 1 レコードを持ちます。レコードは、`.vrma` のデータ、説明、タグ、体の部位(上半身か全身)を持ちます。
- レコードは、長さ、出どころ、必要なボーン、使用回数、オーナーの判断も持ちます。出どころは、同梱、生成、取り込みのどれかです。
- 最初は、コードがマーカーの文をタグと説明に照合します。ライブラリが大きくなったら、埋め込みがこの照合を置き換えます。マーカーの形式は変わりません。
- モーションは、`AnimationMixer` の上半身の層で、0.3〜0.5 秒のクロスフェードで再生します。待機ループは続きます。

表情とモーションは同期させます。

- 表情は別の層ですが、1 つのマーカーが両方を動かします。表情はモーションと一緒に始まり、一緒に終わります。
- 各クリップは、表情のトラックを持てます。マーカーに表情がなければ、コードはクリップの表情を使います。
- マーカーに表情があり、クリップにない場合は、マーカーの表情をクリップの長さだけ再生します。
- モデルに一致する表情がなければ、モーションだけを再生します。

生成:

- 生成は、返答ごとの処理ではありません。テキストからモーションを作るモデルは数秒かかり、固まった指、滑る足、腰の移動を生みます。
- 生成は 2 つの場合に始まります。1 つ目は、オーナーが動きを頼んだときです。例は「剣を振って」です。キャラクターは先に短く話し、クリップの準備ができたら再生します。
- 2 つ目は、マーカーに一致するクリップがないときです。最も近いクリップを再生し、後で使うために生成をキューに入れます。
- 生成器は、アプリが HTTP で呼ぶ外部のサービスです。デスクトップ版と web 版は、同じサービスを使います。
- 生成したクリップの再生では、下半身を固定し、腰の移動を制限します。指のポーズをプリセットで設定し、回転を滑らかにします。
- オーナーは、生成した各クリップを、設定画面で残すか削除します。残したクリップはライブラリに留まります。
- オーナーはどのモーション素材元も許容します。コミュニティのツール Text-To-VRMA があります。この ADR は、そのライセンスと品質を検証していません。

### 記憶と端末

長期記憶と端末間の同期は、別の ADR で扱います。この ADR は、次の点でその ADR に依存します。

- 後から接続した端末も、同じ記憶と会話を受け取ります。
- サーバーが、端末間の発言権のための在席の記録を持ちます。
- 発話の型 `recall` と雑談の種は、1 つの検索インターフェースを通して記憶を読みます。
- ミッション、意図、タイムラインのメモは、同期の設計が運べるレコードです。フレームは、発話モデルに送る場合を除き、端末から出ません。
- 予定している方向は、サーバーを正の保存場所にすることです。バックエンドのスタックが既に持つ VectorChord 入りの PostgreSQL と、EmbeddingGemma 2 を使います。

### プライバシー

発話モデルはクラウドモデルです。フレームが PC の外に出るため、初回リリースから次のルールを必須にします。

- 画面の知覚はオプトインです。設定画面に、アプリが選択したクラウドプロバイダーにフレームを送ることを明記します。
- 知覚の動作中は、インジケーターを表示します。1 クリックで一時停止できます。
- 除外リストに、アプリとウィンドウタイトルを指定します。一致したフレームはスキップします。既定のリストには、パスワードマネージャー、銀行、メッセンジャーを含めます。
- web 版では、画面全体の共有に除外リストが働きません。設定画面はこれを明記し、1 つのウィンドウか 1 つのタブの共有を推奨します。
- 知覚は、サスペンド時、ロック画面時、ソースが消えたときに一時停止します。
- アプリは、フレームをディスクに保存しません。評価用のレコーダーだけが例外です。

レコーダーは、次のルールに従います。

- 開発者向けのツールです。オーナーが開始したときだけ動き、動作中はインジケーターを表示します。
- 各録画を、設定画面が示す 1 つのフォルダーに保存します。設定画面から各録画を削除できます。
- 除外リストは、レコーダーにも適用されます。
- 録画が端末の外に出ることはありません。

### ゲームの音声(後で)

ストーリーのあるゲームは、セリフの音声で出来事を伝えます。ゲームの音声の文字起こしをタイムラインに入れれば、実況が物語を追えます。

- 文字起こしは長時間動くため、ローカルの音声認識モデルを使います。
- システムの音声には、Discord の通話の友人の声も含まれることがあります。その発話を、ゲームのセリフとしてタイムラインに入れてはいけません。
- そのため、キャプチャは 1 つのプロセスの音声だけを取ります。対象ウィンドウを持つプロセスです。
- Windows は 1 つのプロセスのキャプチャに対応していますが、Electron はそれを公開していません。デスクトップ版には、そのためのネイティブモジュールが必要です。
- ゲームの音声を持つのは、Windows のデスクトップ版だけです。オーナーがそれを必要とするのは、PC を使っている間だけです。
- Discord の音声通話への参加は、将来の ADR で扱います。通話では、ボットが話者ごとに 1 つの音声ストリームを受け取るため、声は分かれたままです。

### 既知のリスク

オーナーは、当面これらのリスクを受け入れます。問題が起きたら、後の変更で表の対策を追加します。

| リスク | 待つ理由 | 必要になったときの対策 |
| --- | --- | --- |
| マイクがキャラクターの発話を拾い、キャラクターが自分で止まるか、自分に答える。 | オーナーはヘッドホンを使います。 | エコーキャンセル、再生中の音声との照合、`speaker-tracker` による話者の確認。 |
| 画面の文字が、モデルへの指示として働く。例は「リマインドを追加して」。 | まだ問題は起きていません。 | ターンの種類ごとにツールを制限する。画面がきっかけのターンは、ミッションの作成と記憶の書き込みができない。画面の文字を信頼しないデータとして示す。 |
| 通話中や会議中にキャラクターが話す。 | オーナーは Discord の通話で AIRI を使う予定のため、固定のミュートのルールは合いません。 | AIRI が通話に参加しているかを知る、おやすみモードのルール。 |

## 実装の境界

- `packages/core-agent` が、移植可能なポリシーを持ちます。圧力、閾値、ゲート、予算、発話の型、意図、ミッションのルール、話題の熱、タイムラインです。これらは、時計と乱数源を入力に取る純粋関数です。
- `packages/stage-shared` が、フレームの比較、検出器、フレームポリシーを持ちます。Vue への依存はありません。
- `packages/stage-ui` が、ストア、リングバッファ、判断ターン、ミッションのストア、ツール、アダプターのインターフェース、使用量の記録、インスペクターを持ちます。
- `packages/stage-ui-three` が、モーションの層、ライブラリの再生、マーカーの再生を持ちます。
- `apps/stage-tamagotchi/src/main` が、アイドル時間とウィンドウ一覧を持ちます。Eventa コントラクトは `apps/stage-tamagotchi/src/shared` に置きます。
- `apps/stage-web` が、`getDisplayMedia` と Idle Detection のアダプターを持ちます。
- 文字列は `packages/i18n` に置きます。変更するのは、英語ロケールと作成者のロケールだけです。
- レンダラーのリーダーが、知覚、圧力、ミッションを実行します。他のウィンドウは状態を読むだけです。

## ADR 2026-10-10 との関係

[ADR 2026-10-10](./2026-10-10-skills-automations-and-memory.md) は、レシピと自動実行レシピを定義しています。2026-10-30 の時点で、upstream の `main` には automation のコードも `builtIn_armRecipe` ツールもありませんでした。

- ミッションのテンプレートは、`mission` ブロックを持つレシピです。IndexedDB のレシピの保存を使います。
- `reminder` は、その ADR の `modelTimed` の実行に対応します。`commentary` と `small-talk` には対応するものがありません。声を持つ前景モードだからです。
- `trigger`、`condition`、`cooldown` などの名前は、その ADR に合わせます。
- ミッションに関わる各ステップの前に、upstream の作業を確認します。

## 検証

意見だけでは、振る舞いを判定できません。リプレイ評価は、同じ入力で方式を比較します。

- ステップ 0〜2 は、偽の時計を使った合成イベントストリームを使います。ステップ 3 で、時刻付きのフレームと音声を保存するレコーダーと、録画から知覚と判断を実行するリプレイを追加します。
- 指標は、1 分あたりのターン数、沈黙の割合、書き出しと構造の重複(`distinct-n`)、発話の型のエントロピー、1 時間あたりの送信画像枚数です。
- 追加の指標は、時刻どおりに話したリマインドの割合、1 分あたりの割り込みの数、連続するターンの話題の近さです。
- 話題の近さには目標の範囲があります。高すぎる値は話題の停滞を、低すぎる値はつながりのない飛躍を意味します。
- リプレイは、同じ録画で各フレームポリシーを実行します。画像枚数、トークン数、キャッシュの割合、費用を記録します。
- 判定モデルが、発話がその窓の中の実際のイベントに触れているかを確認します。別のチェックが、タイムラインとの矛盾を見つけます。
- 評価は、`evals/asr-rewrite` と `evals/tts-speech-formula` の形式に従います。
- 偽の時計と固定の乱数源を使った決定的テストで、圧力、ゲート、予算、発話の型、意図、オーナーによる調整、話題の熱、ミッションを検証します。
- 実際のクラウドモデルと実際の画面を使ったライブ確認は、CI の対象外です。結果は PR に記録します。
